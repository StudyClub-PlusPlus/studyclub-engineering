# Voice Channel Activity Monitor (공부방 활동 감시)

앵커 카테고리 아래 스터디들의 **공부방(음성 채널)마다 마지막 입·퇴장 시각**을 SQLite 에 적어 두고,
**3주 동안 아무 입·퇴장도 없었던 공부방**을 alert 채널에 알린다. 지금 상태를 바로 보고 싶으면
`!checkVoiceChannels` 가 `카테고리 - 공부방 : 마지막 활동일` 을 전부 출력한다.

> ✅ **구현됨** — [`discord/app/voice_activity_log.py`](../../discord/app/voice_activity_log.py) (SQLite) +
> [`discord/app/bot/voice_monitor.py`](../../discord/app/bot/voice_monitor.py) (리스너 · 매일 점검) +
> [`discord/app/bot/commands/voice_monitor_cmd.py`](../../discord/app/bot/commands/voice_monitor_cmd.py),
> 테스트는 [`test_voice_activity_log.py`](../../discord/tests/test_voice_activity_log.py) ·
> [`test_voice_monitor.py`](../../discord/tests/test_voice_monitor.py) ·
> [`test_voice_monitor_cmd.py`](../../discord/tests/test_voice_monitor_cmd.py).
> [결정과 남은 질문](#결정과-남은-질문)의 11개 항목은 **전부 표대로 구현했다** (#3 · #4 · #5 · #6 · #9 · #10 은
> 2026-09-30 리뷰에서 확정, 나머지는 추천안대로). 이 문서는 **왜 그렇게 만들었는지**의 원본이다 —
> 코드와 어긋나면 코드를 보고 이 문서를 고친다.
> **길드 쪽 준비는 없다** — 새 환경변수도, 새 채널도, 인텐트 변경도 필요하지 않다
> ([설정값](#설정값)). 실제 길드에서의 손 확인([구현 단계](#구현-단계) 10번)은 **아직 안 했다.**
> 형식과 서술 방식은 [`voice-channel-bulletin.md`](voice-channel-bulletin.md) 를 따랐다.

## 미리 알아야 할 것

[게시판 문서의 용어표](voice-channel-bulletin.md#미리-알아야-할-것)(카테고리 · 앵커 · 음성 채널 · 채널 멘션)를
그대로 쓴다. 여기서 새로 나오는 것만 적는다.

| 용어 | 뜻 |
|------|-----|
| **voice state** | 어떤 멤버가 **지금 어느 음성 채널에 있는지**를 나타내는 Discord 의 상태값. 음소거·헤드셋 끔·화면 공유 여부도 같이 들어 있다 |
| **`on_voice_state_update`** | voice state 가 바뀔 때마다 봇이 받는 이벤트. **입장·퇴장뿐 아니라 음소거·화면공유 토글에도 똑같이 온다** — 그래서 입·퇴장만 골라내는 판정이 필요하다 ([무엇을 "활동" 으로 보나](#무엇을-활동-으로-보나)) |
| **게이트웨이 이벤트는 재생되지 않는다** | 봇이 꺼져 있는 동안 일어난 입·퇴장은 **켠 뒤에 받아볼 방법이 없다.** 이 기능의 가장 큰 한계고, [구조적 한계](#구조적-한계-미리-인정하는-것)에서 따로 다룬다 |
| **관찰 시작일 (`first_seen_at`)** | 그 공부방을 이 기능이 **처음 본 날.** 활동 기록이 아직 없는 채널의 "3주" 를 **이 날부터** 센다 — 안 그러면 어제 만든 공부방도 즉시 "3주 무활동" 이 된다 |
| **UPSERT** | `INSERT ... ON CONFLICT ... DO UPDATE`. 행이 없으면 넣고 있으면 고치는 한 문장. 이 기능의 쓰기는 전부 이것 하나다 |

비유하자면 **빈 강의실 순찰 기록부**다. 관리인(봇)이 문이 열리고 닫힐 때마다 **그 방 칸에 날짜만 고쳐 적고**,
매일 저녁 기록부를 훑어 **3주 넘게 아무도 안 들어간 방**을 운영진에게 보고한다.
기록부는 방마다 한 줄이고, 방문 일지처럼 쌓이지 않는다.

## 왜 필요한가

스터디는 만들어지고 나서 조용히 죽는다. 카테고리와 공부방은 사이드바에 남아 있어서,
**사이드바만 보면 살아 있는 스터디와 죽은 스터디가 구분되지 않는다.**
운영진이 "요즘 안 쓰는 스터디" 를 알려면 지금은 방마다 눈으로 확인해야 한다.

**공부방에 사람이 들어온 마지막 날짜 하나**만 있으면 그 판단이 끝난다.
그게 이 기능의 전부다 — 누가 얼마나 있었는지, 몇 명이 모였는지는 **목적이 아니다.**

## 결과물

두 가지다.

**1. 매일 alert 채널에 올라가는 알림** (3주 이상 조용한 공부방이 있을 때만):

```
3주(21일) 이상 입·퇴장이 없는 공부방이 2개 있습니다. (기준일: 2026-09-30)
알고리즘 스터디 - 공부방-알고리즘 스터디 : 2026-08-20
영어 회화 - 공부방-영어 회화 : 기록 없음 (관찰 시작 2026-08-25)
```

**2. `!checkVoiceChannels` 의 답장** (요청받은 형식 그대로, 사이드바 순서):

```
알고리즘 스터디 - 공부방-알고리즘 스터디 : 2026-08-20
알고리즘 스터디 - 공부방-2조 : 2026-09-29
CS 전공 스터디 - 공부방-CS 전공 스터디 : 2026-09-30
영어 회화 - 공부방-영어 회화 : 기록 없음 (관찰 시작 2026-08-25)
```

- **형식은 `카테고리 - 공부방 : 날짜`** 다. 셋 다 ` - ` 로 잇는 안을 2026-09-30 리뷰에서 뒤집었다 —
  구분자가 전부 같으면 **어디까지가 채널 이름인지 눈으로 끊을 수 없다.** 공부방 이름에 하이픈이
  들어가는 것(`공부방-알고리즘 스터디`)이 규칙이라 특히 그렇다. ` : ` 가 **"이름들 / 값" 의 경계**를 맡고,
  ` - ` 는 이름들 사이에만 남는다. 알림 메시지도 같은 형식을 쓴다.
- **채널 멘션(`<#id>`)이 아니라 채널 이름**을 쓴다. 게시판과 반대인데, 이건 **눌러서 들어가는 안내판이 아니라
  읽는 보고서**여서 그렇다. 칩으로 렌더되면 `카테고리 - 채널 : 날짜` 의 칸 정렬이 깨진다.
- 활동 기록이 없는 방은 `기록 없음 (관찰 시작 yyyy-mm-dd)` 이다 — 빈 칸으로 두면 "오래된 방" 과
  "이제 막 보기 시작한 방" 이 구분되지 않는다.

## 결정과 남은 질문

**✅ 는 2026-09-30 리뷰에서 확정된 줄**이고, 나머지는 이 문서의 추천안이다 (뒤집지 않으면 그대로 간다).

| # | 질문 | 결정 / 추천 | 왜 이쪽인가 / 다른 선택지 |
|---|------|------|--------------------------|
| 1 | 알림을 **어디로** 보내나 | **`DISCORD_ALERT_CHANNEL_ID` 재사용** (새 환경변수 없음) | 이건 운영 알림이고, alert 채널은 이미 그 용도로 있다. 새 채널을 쓰려면 env var·README·배포 설정이 같이 늘어난다. 나중에 분리하고 싶으면 `DISCORD_VOICE_ALERT_CHANNEL_ID` 를 추가하고 없으면 alert 로 떨어지게 하면 된다 |
| 2 | `!checkVoiceChannels` 는 **누가** 쓸 수 있나 | **captain 전용** (`!updateBulletin` 과 동일) | 길드 전체의 활동 현황을 한 번에 뿌리는 명령이다. "우리 스터디가 죽은 것으로 보인다" 는 정보가 아무 채널에서나 나오면 곤란하다. `may_update` 와 같은 모양으로 `may_check` 를 둔다. 전원 허용으로 바꾸려면 검사 한 줄을 지우면 된다 |
| 3 | 무활동 기준은 **얼마**이고, 환경변수로 뺄까 | ✅ **3주 — 상수 `INACTIVITY = timedelta(weeks=3)`** | 처음 요청은 4주였는데 2026-09-30 리뷰에서 **3주로 줄였다**: 한 달을 기다리면 이미 스터디가 흩어진 뒤다. 환경변수로 빼지 않는 건 게시판의 갱신 시각과 같은 판단이다 — 요청에 없었고, 바뀌면 상수 한 줄을 고치는 게 싸다 |
| 4 | 활동 기록이 **없는** 채널의 3주는 언제부터? | ✅ **관찰 시작일(`first_seen_at`)부터** | epoch 부터 세면 배포 첫날 모든 공부방이 알림에 실린다. 채널 생성일(`channel.created_at`)을 쓰는 방법도 있는데, **그러면 배포 전부터 있던 방이 곧바로 3주 초과**로 잡힌다. "우리가 본 날부터" 가 우리가 실제로 아는 사실이다 |
| 5 | 같은 채널에 **재알림**을 언제 하나 | ✅ **활동이 다시 생길 때까지 1회만** (`last_alerted_at` 을 쓰고, 활동이 들어오면 지운다) | 매일 같은 목록이 올라오면 alert 채널을 아무도 안 읽게 된다. 대신 지금 상태는 언제든 `!checkVoiceChannels` 로 볼 수 있다. 다른 선택지: 매주 재알림 — 놓친 알림을 다시 띄워 주지만 소음이 늘어난다 |
| 6 | 앵커 아래 카테고리 훑는 코드를 **어떻게 공유**하나 | ✅ **공유하지 않는다 — `voice_monitor.py` 에 따로 쓴다.** 게시판 코드는 **한 줄도 건드리지 않는다** | 게시판의 `collect_categories` 는 `(이름, 채널ID들)` 을 주는데 이 기능은 **채널 객체**(이름 때문에)가 필요하다. 공용 모듈로 빼는 안도 있었지만, 2026-09-30 리뷰에서 **지금은 복제**로 정했다: 돌고 있는 게시판을 리팩터하는 위험보다, 규칙이 두 곳에 있는 값이 지금은 더 싸다. **대가는 [미정 사항](#미정-사항) 2 에 적었다** — 앵커 규칙이 바뀌면 **두 곳을 고쳐야 한다** |
| 7 | **봇 계정**의 입·퇴장도 활동인가 | **무시한다** (`member.bot` 이면 기록하지 않음) | 음악봇이 들어와 있는 방은 "쓰이는 방" 이 아니다. 우리 봇 자신도 마찬가지다 |
| 8 | 3주 내내 **접속을 안 끊은** 방은? | **매일 점검에서 "지금 사람이 있으면 활동으로 기록"** 한다 | 이벤트만 믿으면 계속 켜 둔 방이 조용한 방으로 보인다. 점검 때 `channel.voice_states` 가 비어 있지 않으면 그날로 찍는다. 이게 다운타임 복구에도 일부 도움이 된다 (#9) |
| 9 | 봇이 **꺼져 있던 동안**의 활동은? | ✅ **유실을 인정하고 문서화한다** (2026-09-30 리뷰에서 명시적으로 받아들였다) | 게이트웨이 이벤트는 재생되지 않고, Discord 에 "이 채널의 마지막 입장" 을 물어보는 API 도 없다. #8 덕분에 "재시작 시점에 사람이 있던 방" 은 건진다. 알림은 **파괴적 동작이 아니라 사람이 확인할 제보**라서, 드문 오탐을 감수할 수 있다 |
| 10 | 채널이 **삭제되면** 그 행은? | ✅ **`on_guild_channel_delete` 로 지운다** (2026-09-30 리뷰) | discord.py 2.4.0 이 이 이벤트를 주는 것을 라이브러리 소스에서 확인했고, 필요한 `guilds` 인텐트는 기본으로 켜져 있다. 리스너 하나와 `DELETE` 한 줄이면 **DB 가 길드를 그대로 따라간다** — 지운 방이 기록부에 남아 있지 않은 편이 사람이 DB 를 직접 들여다볼 때 덜 헷갈린다. 행을 남겨도 보고에는 안 섞이지만(보고는 길드 기준), 그건 "안 읽히니 괜찮다" 는 것이고 지우는 편이 정확하다 |
| 11 | 점검을 **언제** 돌리나 | **매일 20:00 America/Los_Angeles** (게시판과 같은 시각, 상수는 따로) | 하루 한 번이면 충분하고, 기준이 하나뿐인 편이 설명하기 쉽다. 게시판의 `BULLETIN_TIME` 을 **import 하지는 않는다** — 관계없는 두 스케줄이 상수 하나로 묶이면 한쪽을 옮길 때 다른 쪽이 조용히 따라간다 |

## 설계

### 설정값

**새 환경변수가 없다** (#1). 기존 값만 읽는다.

| 기존 환경변수 | 이 기능에서의 뜻 | 비우면 |
|----------------|------------------|--------|
| `DISCORD_GUILD_ID` | 기록·점검 대상 길드 | 기록도 점검도 안 한다 (경고 로그 1회) |
| `DISCORD_ALERT_CHANNEL_ID` | 알림이 가는 채널 | **기록은 계속한다 — 점검 루프도 돌지만 스냅샷만 찍고 보고는 하지 않는다** (경고 로그 1회) |
| `DISCORD_CAPTAIN_ROLE_ID` | `!checkVoiceChannels` 를 쓸 수 있는 역할 | 명령을 **거부**한다 (`may_update` 와 같은 태도) |

- **"기록" 과 "알림" 의 켜짐 조건이 다르다.** alert 채널이 없다고 기록까지 멈추면, 나중에 채널을 설정한
  날부터 다시 3주를 기다려야 한다. 기록은 값이 싸고 되돌릴 수 없는 손실을 막는다.
- **alert 채널에 걸리는 것은 보고 단계뿐이다.** 점검 루프는 채널이 없어도(또는 ID 가 틀려 못 찾아도)
  똑같이 돌면서 스냅샷(`observe` + 재실 중 `touch`)을 찍고, 판정·알림만 건너뛴다. 입·퇴장 이벤트만으로는
  **아무도 안 들어간 방에 행이 생기지 않아서**, 스냅샷이 없으면 그 방들은 결국 채널을 설정한 날부터
  3주를 기다리게 된다 — 위 문단이 막으려던 바로 그 대기다. 알리지 못한 방은 `last_alerted_at` 을
  채우지 않으므로, **채널이 생긴 뒤 첫 점검에서 그동안 조용했던 방이 한꺼번에 보고된다.**
- Discord 인텐트는 **고칠 것이 없다.** `discord.Intents.default()` 에 `voice_states` 가 이미 켜져 있고
  (`discord.py==2.4.0` 에서 확인), `on_voice_state_update` 의 `member` 는 이벤트 payload 로 만들어지므로
  **`members` 인텐트 없이도 온다.** 라이브러리 소스에서 확인한 사실이라 [한계](#구조적-한계-미리-인정하는-것)에
  근거를 적어 뒀다 — `channel.members` 를 쓰면 안 되는 이유가 여기서 나온다.

### 무엇을 "활동" 으로 보나

`on_voice_state_update(member, before, after)` 는 **음소거·헤드셋 끔·화면 공유·카메라 토글에도 온다.**
요청은 입장과 퇴장뿐이므로 **채널이 바뀐 이벤트만** 본다:

```python
if before.channel == after.channel:
    return            # 음소거 등 -- 채널 이동이 아니다
```

- **입장**: `after.channel is not None` → 그 채널을 찍는다.
- **퇴장**: `before.channel is not None` → 그 채널을 찍는다.
- **방 이동**: 위 두 줄이 다 걸려 **두 채널을 모두** 찍는다. 나간 것도 활동이고 들어온 것도 활동이다.
- **봇은 무시** (#7): `member.bot` 이면 아무것도 찍지 않는다.
- **다른 길드는 무시**: `member.guild.id != settings.guild_id` 면 끝낸다.

`before`/`after` 의 `channel` 이 퇴장 시에도 남아 있는지 확인했다 — 라이브러리가 `before` 를 갱신 **전에**
복사하므로, 퇴장 이벤트의 `before.channel` 은 떠난 방을 그대로 가리킨다.

**채널이 지워지면 행도 지운다** (#10). 같은 파일의 두 번째 리스너다:

```python
@bot.listen("on_guild_channel_delete")
async def forget_deleted_channel(channel: discord.abc.GuildChannel) -> None:
    if isinstance(channel, discord.VoiceChannel) and channel.guild.id == settings.guild_id:
        log.forget(channel.id)
```

- 음성 채널만 지운다. 텍스트 채널·카테고리는 애초에 행이 없어서 `DELETE` 가 헛돈다.
- **카테고리만 지운 경우는 이벤트가 오지 않는다** — Discord 는 카테고리를 지울 때 안의 채널을 함께
  지우지 않고 카테고리 밖으로 내보낸다. 그 방들은 앵커 아래 어느 카테고리에도 없으니 **보고에서 빠지고**,
  행은 남는다. 방을 정말 지우면 방마다 이벤트가 온다.
- **봇이 꺼져 있는 동안 지워진 채널의 행은 남는다.** 보고는 길드에 실제로 있는 채널만 돌기 때문에
  **결과에 영향이 없고**, 그 행은 다시 안 읽힌다. 되살아나는 사고도 없다 — 같은 이름으로 방을 다시
  만들어도 **채널 ID 가 달라서** 새 행이 된다. 그래서 이 유실은 고치지 않는다.
- 봇이 **볼 수 없는** 채널은 캐시에 없어서 이벤트도 오지 않는다. 그 채널은 보고 대상도 아니었다.

**앵커 아래인지는 이벤트에서 따지지 않는다.** 길드의 모든 음성 채널을 기록하고,
**보고·알림 때만** 앵커 아래로 걸러낸다 ([어떤 공부방을 보고하나](#어떤-공부방을-보고하나)). 이유:

- 이벤트 경로가 `O(1)` 로 끝난다. 앵커를 찾으려면 매 이벤트마다 `guild.categories` 를 다시 만들어야 하는데,
  그건 채널 수에 비례하는 일이고 입·퇴장은 게시판 갱신보다 훨씬 자주 일어난다.
- 카테고리를 나중에 앵커 아래로 옮긴 스터디도 **그 전의 기록을 그대로 갖는다.**
- 앵커가 사라져도 **기록은 계속 쌓인다** (게시판은 앵커가 없으면 멈춰야 하지만, 여기선 멈출 이유가 없다).

### 어디에 적나 (SQLite)

기존 `data/discord.sqlite3` (`settings.db_path`) 에 **테이블 하나를 더한다.**
`app/study_reservations.py` 와 **완전히 같은 모양**의 모듈 `app/voice_activity_log.py` 를 만든다 —
`_connect()` 가 `CREATE TABLE IF NOT EXISTS` 를 돌리고, 메서드마다 짧은 연결을 열고 닫는다.

```sql
CREATE TABLE IF NOT EXISTS voice_channel_activity (
  channel_id       INTEGER PRIMARY KEY,  -- 음성 채널 ID
  first_seen_at    TEXT NOT NULL,        -- 관찰 시작 (ISO8601 UTC)
  last_activity_at TEXT,                 -- 마지막 입·퇴장. NULL = 관찰 이후 활동 없음
  last_alerted_at  TEXT                  -- 마지막 알림. NULL = 아직 알리지 않음 (#5)
)
```

| 메서드 | 하는 일 |
|--------|---------|
| `observe(channel_ids, now)` | 없는 채널만 `INSERT OR IGNORE` 로 넣는다 (`first_seen_at = now`). 이미 있으면 **아무것도 안 건드린다** |
| `touch(channel_id, now)` | UPSERT: `last_activity_at = now`, **`last_alerted_at = NULL`**. 그 NULL 이 다음 3주 뒤의 알림을 다시 무장시킨다 (#5) |
| `rows()` | `{channel_id: (first_seen_at, last_activity_at, last_alerted_at)}` 전체를 준다. 길드의 채널 수만큼이라 통째로 읽어도 된다 |
| `mark_alerted(channel_ids, now)` | 방금 알린 채널들의 `last_alerted_at` 을 채운다. `now`(점검 시각) 이후에 입·퇴장이 있었던 채널은 **건너뛴다** — 알림을 보내는 사이의 입장이 지운 표시를 다시 채우면 다음 침묵이 묻힌다 |
| `forget(channel_id)` | 그 채널의 행을 지운다 (#10). 행이 없어도 조용히 끝난다 — 텍스트 채널이 지워져도 같은 코드가 불린다 |

- **채널 이름·카테고리 이름은 저장하지 않는다.** 이름은 바뀌고, 바뀐 이름은 길드가 이미 알고 있다.
  게시판이 `<#id>` 를 쓰는 것과 같은 이유다 — **DB 에는 ID 와 시각만, 이름은 읽을 때 길드에서.**
- **이벤트마다 쓴다. 캐시나 배치는 두지 않는다.** 입·퇴장 하나가 UPSERT 한 번(연결 열기 포함 1ms 안쪽)이고,
  스터디 클럽 규모에서 초당 수십 번 날 일이 없다. 기존 `StudyReservations` 도 같은 방식으로 요청 경로에서
  동기 sqlite 를 쓴다. 정말 부담이 되면 **표시 단위가 하루**라는 점을 이용해 "같은 날 이미 찍었으면 건너뛰기"
  를 프로세스 메모리 dict 로 넣을 수 있다 — [미정 사항](#미정-사항) 3 에 조건과 함께 남겼다.

### 어떤 공부방을 보고하나

**앵커 카테고리 아래의, 봇이 볼 수 있는 음성 채널** — 게시판과 정확히 같은 집합이지만,
**순회 코드는 공유하지 않고 이 기능 안에 따로 쓴다** (#6):

```python
# app/bot/voice_monitor.py -- bulletin.collect_categories 와 같은 규칙, 반환형만 다르다
def collect_study_voice_channels(
    guild: discord.Guild, anchor_name: str
) -> list[tuple[discord.CategoryChannel, list[discord.VoiceChannel]]] | None:
    """앵커 아래 (카테고리, 보이는 음성채널들). 앵커가 없으면 None."""
```

- 규칙은 [게시판 문서](voice-channel-bulletin.md#어떤-음성-채널을-모으나)와 **글자 그대로 동일하다**:
  position 순, 같은 이름이면 맨 위가 앵커, 앵커 자신은 제외,
  `permissions_for(guild.me).view_channel` 인 채널만. 다른 점은 ID 대신 **채널 객체**를 준다는 것뿐이다
  (리포트에 이름이 필요하다).
- **[`bulletin.py`](../../discord/app/bot/bulletin.py) 는 건드리지 않는다.** 그래서 게시판 쪽 무회귀를
  증명하는 방법이 "테스트가 통과한다" 가 아니라 **"파일이 diff 에 없다"** 가 된다.
- 이 복제가 **의도된 빚**이라는 표시를 코드에 남긴다: 두 함수의 docstring 이 서로를 가리키고,
  "앵커 규칙을 고치면 둘 다 고쳐라" 를 적는다. 근거는 [미정 사항](#미정-사항) 2.
- **앵커가 없으면(`None`) 보고도 알림도 하지 않는다** — 게시판의 결정 3 과 같다. 앵커가 없으면 스터디와
  운영 카테고리를 구분할 수 없고, 운영 카테고리의 회의방을 "죽은 스터디" 로 알리는 건 사고다.
- 읽을 때마다 **먼저 `observe()` 를 돌린다**: 길드에 보이는 채널 전부가 행을 갖게 되므로,
  방금 만든 공부방도 `기록 없음 (관찰 시작 오늘)` 으로 정확히 나온다.
  점검 루프와 `!checkVoiceChannels` 가 **같은 함수를 공유**한다.

### 매일 점검 루프

게시판의 루프와 같은 방식이다 ([왜 간격이 아니라 시각인지](voice-channel-bulletin.md#언제-돌리나)는 그 문서에).

```python
INACTIVITY_CHECK_TIME = datetime.time(hour=20, tzinfo=ZoneInfo("America/Los_Angeles"))  # #11
INACTIVITY = datetime.timedelta(weeks=3)                                                # #3
```

한 번 돌 때 하는 일, 순서대로:

1. 길드를 확인한다. 없으면 로그만 남기고 끝낸다. alert 채널도 여기서 찾아 두지만,
   **없거나 못 찾아도 끝내지 않는다** — 4번까지는 그대로 간다 ([설정값](#설정값)).
2. 앵커 아래 (카테고리, 음성채널들) 을 모은다. 앵커가 없으면 **로그 + alert 통지 후 끝** (판단하지 않는다).
3. 보이는 채널 전부를 `observe()` 로 등록한다 (새 방의 관찰 시작일).
4. **지금 사람이 있는 방을 `touch()`** 한다 (#8) — 판정 **전에** 해서, 계속 켜 둔 방이 오탐되지 않게 한다.
   판정은 `bool(channel.voice_states)` 로 한다. **`channel.members` 를 쓰면 안 된다** —
   [한계](#구조적-한계-미리-인정하는-것) 참고. **alert 채널이 없으면 여기서 끝낸다.**
5. `rows()` 를 읽고, `now - (last_activity_at or first_seen_at) >= INACTIVITY` 인 채널을 고른다.
6. 그중 `last_alerted_at is None` 인 것만 알린다 (#5). 하나도 없으면 **메시지를 보내지 않는다** —
   "이상 없음" 을 매일 올리면 알림을 읽지 않게 된다.
7. 알린 채널들을 `mark_alerted()` 한다.

- 등록 위치와 시작 시점은 게시판과 같다: `create_bot` 에서 `register(bot, settings)` 로 걸고
  **`setup_hook` 에서 `start()`** 한다. `create_bot` 안에서 바로 시작하면 `wait_until_ready()` 가
  로그인 전 클라이언트에서 던져 **루프가 영구히 죽는다** (게시판 구현 중 실제로 밟은 함정이다).
  기존 `setup_hook` 은 덮지 않고 이어 붙인다.
- `before_loop` 에서 `wait_until_ready()` 뒤 **한 번 즉시** 돌린다. 배포 직후 관찰 시작일이 찍혀야
  3주 시계가 돌기 시작하고, 재시작 시점에 사람이 있던 방도 그때 건진다 (#9).
- **이벤트 리스너도 루프도 alert 채널과 무관하게 항상 등록한다** ([설정값](#설정값)).

### 알림 메시지

```
3주(21일) 이상 입·퇴장이 없는 공부방이 {N}개 있습니다. (기준일: {yyyy-mm-dd})
{카테고리} - {공부방} : {yyyy-mm-dd}
...
```

- 본문을 만드는 것은 **순수 함수**다 (`build_inactivity_alert(entries, today)`), Discord 없이 테스트한다.
- 2000자 한도 처리는 게시판과 같다: **줄 단위로만 자르고**, 마지막에 `…외 {N}개는 !checkVoiceChannels 로
  확인해 주세요.` 를 붙인다. 잘렸다는 사실을 경고 로그로 남긴다.
- `allowed_mentions=discord.AllowedMentions.none()` 을 건다. 본문이 **카테고리·채널 이름**이라서
  이름에 `@everyone` 이 들어 있으면 길드 전체가 울린다 — 게시판보다 더 현실적인 위험이다(거긴 ID 만 쓴다).
- 통지는 `resolve_configured_channel(guild, settings.alert_channel_id, "alert")` 로 채널을 얻는다
  (기존 함수 재사용).

### `!checkVoiceChannels`

`app/bot/commands/voice_monitor_cmd.py`. `bulletin_cmd.py` 와 **같은 모양**이다 —
`may_check(ctx, settings)` + 순수하게 테스트 가능한 코루틴 + `register(bot, settings)`.

```
!checkVoiceChannels
→ 알고리즘 스터디 - 공부방-알고리즘 스터디 : 2026-08-20
  알고리즘 스터디 - 공부방-2조 : 2026-09-29
  영어 회화 - 공부방-영어 회화 : 기록 없음 (관찰 시작 2026-08-25)
```

- **captain 전용** (#2). `DISCORD_CAPTAIN_ROLE_ID` 가 비어 있으면 거부하고, DM 도 거부한다.
- 앵커를 못 찾으면 **그렇다고 답장한다** (조용히 빈 목록을 주면 "공부방이 없다" 로 읽힌다).
- 보고할 공부방이 하나도 없으면 `지금 앵커 아래에 공부방이 없습니다.` 한 줄. 빈 메시지는 Discord 가 거부한다.
- **2000자를 넘으면 여러 메시지로 나눠 보낸다** — 알림과 다른 선택이다. 알림은 "이상이 있다" 는 신호라서
  잘려도 목적을 이루지만, 이 명령은 **전체를 보려고** 부른 것이라서 자르면 부른 이유가 없어진다.
  줄 단위로 2000자씩 묶어 순서대로 보낸다.
- `sort` 옵션·필터 인수는 두지 않는다. 요청은 전체 출력이다.
- **점검 루프와 같은 스냅샷을 찍는다** (`record_snapshot`): `observe()` 뿐 아니라 **지금 사람이 있는 방도
  `touch()`** 한다. 구현하면서 갈린 지점이다 — 명령이 `observe()` 만 하면, 3주째 접속을 끊지 않은 방이
  **목록에는 오래된 날짜로 보이는데 알림은 오지 않는** 상태가 된다. 두 출력이 같은 사실을 말해야 한다.
- 연타 제한(cooldown)은 두지 않는다 — captain 만 쓰고, 읽기 한 번에 sqlite 한 번이다.

### 시각 표기

- **저장은 UTC ISO8601** (`datetime.now(timezone.utc).isoformat()`). DB 에 현지 시각을 넣으면
  DST 전환 구간에서 두 번 나타나는 시각이 생긴다.
- **표시는 `America/Los_Angeles` 의 날짜** (`yyyy-mm-dd`). 게시판이 태평양 시간을 쓰므로 같은 기준을 쓴다.
  UTC 로 보여 주면 저녁에 쓴 방이 다음 날짜로 찍힌다.
- **판정은 시각끼리 뺀다** (`now - last >= timedelta(weeks=3)`), 날짜 문자열을 비교하지 않는다.
  표시 단위가 하루라는 것과 판정 정확도는 별개다.

### 실패했을 때

게시판과 같은 태도다 — **아무도 기다리지 않는 백그라운드 작업이므로, 어떤 실패도 프로세스를 죽이지 않고
대신 보이게 만든다.**

| 상황 | 하는 일 |
|------|---------|
| `DISCORD_GUILD_ID` 없음 | 경고 로그 1회, 리스너·루프 모두 미동작 |
| `DISCORD_ALERT_CHANNEL_ID` 없음 | 경고 로그 1회, **기록은 계속** (매일 스냅샷 포함), 보고만 생략 |
| 앵커 카테고리 없음 | 에러 로그 + alert 통지, **판정하지 않음** |
| alert 채널을 못 찾음 / 권한 없음 | 에러 로그 (통지할 곳이 그 채널이므로 로그가 전부다). 못 찾은 경우에도 **스냅샷은 찍는다** |
| 삭제 이벤트 처리 중 sqlite 오류 | `logger.exception` 으로 삼킨다. 남은 행은 보고에 섞이지 않으므로 **지우지 못한 것이 오류로 이어지지 않는다** |
| 입·퇴장 이벤트 처리 중 sqlite 오류 | `logger.exception` 으로 삼킨다 — 리스너에서 예외가 새면 discord.py 가 로그만 남기지만, 입·퇴장 하나 때문에 시끄러워질 이유가 없다 |
| 점검 루프 안의 그 밖의 예외 | `logger.exception` 으로 삼켜 **다음 날에도 루프가 계속 돌게 한다** |
| 2000자 초과 | 알림은 잘라서 보내고 경고 로그, 명령은 나눠 보낸다 |

### 구조적 한계 (미리 인정하는 것)

**리뷰에서 "이건 왜 안 맞나" 를 다시 묻지 않기 위해 적는다.**

1. **봇 다운타임 중 활동은 유실된다** (#9). 게이트웨이 이벤트는 재생되지 않고, Discord 에는
   "이 음성 채널의 마지막 입장" 을 묻는 API 가 없다. 재시작 시점에 사람이 있던 방은 #8 이 건진다.
   그래서 **오탐(조용하지 않은데 조용하다고 알림)이 가능하고, 반대 방향 오탐은 없다** —
   알림은 사람이 확인할 제보이고 아무것도 지우지 않으므로 이 방향의 오차가 안전하다.
2. **`channel.members` 를 쓰면 안 된다.** discord.py 의 `VoiceChannel.members` 는 `guild.get_member()`
   로 멤버 캐시를 거치는데, 이 봇은 `members` 인텐트가 꺼져 있어 캐시가 비어 있을 수 있다 —
   그러면 사람이 있는 방도 **빈 방으로 보인다.** 라이브러리가 "멤버 캐시가 없을 때 쓰라" 고 문서화한
   `channel.voice_states`(멤버 ID → voice state dict) 를 쓴다. 봇이 처음 붙을 때 받는 `GUILD_CREATE`
   payload 에 voice state 들이 들어 있어서, **재시작 직후에도 누가 앉아 있는지 알 수 있다.**
3. **"활동" 은 입·퇴장 횟수이지 사용 시간이 아니다.** 1초 들어왔다 나간 것과 3시간 공부한 것이 같다.
   요청이 입·퇴장이었고, 체류 시간을 재려면 방마다 세션을 열고 닫아야 해서 모델이 커진다.
4. **텍스트 채널(`로비-*`) 활동은 보지 않는다.** 요청은 음성 채널이다. 로비에서만 활발한 스터디는
   조용한 것으로 잡힌다.

기존 관례를 따른다 (`unittest.mock` 의 `Mock`/`AsyncMock` + `FakeGuild`, 실제 Discord 연결 없음,

`tests/test_voice_monitor_cmd.py`. **기존 테스트 파일은 하나도 수정하지 않는다** (#6).

## 이번에 하지 않는 것

요청 범위 밖이라 **의도적으로 빼는** 것들.

- **체류 시간·접속 인원·참여자 통계** — 입·퇴장 날짜 하나만 본다 ([한계](#구조적-한계-미리-인정하는-것) 3)
- **텍스트 채널 활동** (`로비-*` 의 메시지) — 요청은 음성 채널이다. 하려면 `message_content` 없이도 되는
  `on_message` 로 가능하지만 별건이다
- **활동 로그 이력** (방문 일지) — 방마다 한 줄만 유지한다. 추이를 보려면 테이블 모양이 달라진다
- 무활동 스터디를 **자동으로 아카이브·삭제** — 알림까지다. 지우는 건 사람이 판단한다
- 조회용 **HTTP 엔드포인트** — 백엔드가 이 데이터를 쓸 이유가 아직 없다
- 3주·점검 시각·알림 문구의 **환경변수화** (#3, #11)
- 알림 대상 스터디의 **captain 을 멘션**하는 것 — 누가 그 스터디의 주인인지 봇이 모른다
  (역할과 카테고리를 잇는 기록이 `study_reservation` 에 있지만 읽기 전용으로 쓸 계획이 없다)
- `!checkVoiceChannels` 의 정렬·필터 옵션, 출력 형식 선택, cooldown
