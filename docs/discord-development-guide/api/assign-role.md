# Assign Discord Role

역할 하나를 여러 유저에게 한 요청으로 붙인다. 스터디 참가 확정처럼 **이미 만들어진 역할**을
멤버들에게 배정하는 용도다 — 역할을 만드는 건 [`create-study.md`](create-study.md), 떼는 건
[`remove-role.md`](remove-role.md) 쪽이다.

> ⚠️ **아직 구현 전이다.** 이 문서는 구현할 계약이다.
> 공통 요청 헤더는 [`common-header.md`](common-header.md) 를 따른다.
> **대상 길드는 하나로 고정**이라 요청에 길드를 넘기지 않는다.

## 요청

```
POST /api/v1/roles/{discordRoleId}/users
```

| 경로 변수 | 타입 | 설명 |
|-----------|------|------|
| `discordRoleId` | string | 붙일 **Discord 역할 ID**(snowflake). `create-study` 가 돌려준 `discordRoleId` 가 여기 들어간다 |

헤더는 [공통 헤더](common-header.md) 전부 — `Idempotency-Key` 는 **필수**다.

**captain 역할을 가진 멤버만 호출할 수 있다.** [`create-study`](create-study.md#요청) 와 같은 규칙이다 —
봇이 `X-Discord-User-ID` 로 길드 멤버를 조회해 captain 역할 보유 여부를 확인하고, 없으면 **403** 이다.
captain 역할은 길드에 **이미 존재하는** 역할이고, 찾지 못하면 배정하지 말고 실패한다.

```jsonc
{
  "discordStudyId": "1327394882193883136",
  "discordUserIds": ["327394882193883136", "412938471293847123"]
}
```

| 필드 | 타입 | 필수 | 제약 |
|------|------|------|------|
| `discordStudyId` | string | O | snowflake. **로깅·추적용**이다 — 아래 설명 참고 |
| `discordUserIds` | string[] | O | snowflake 배열. 1개 이상, 중복은 무시. 상한은 [미정](#미정-사항) |

**모든 ID 는 문자열이다** — snowflake 는 64비트라 JSON 숫자로 보내면 JS 호출자에서 정밀도가
깨진다 ([common-header.md](common-header.md#x-discord-user-id) 와 같은 규칙). `discordRoleId` 는 경로에 있으니
원래 문자열이고, 검증은 헤더와 같은 `^[0-9]{17,20}$` 로 한다.

### `discordStudyId` 의 역할

**어떤 스터디 때문에 이 배정이 일어났는지** 로그에 남기기 위한 값이다. 봇은 이 값으로
무언가를 조회하거나 권한을 판단하지 **않는다**.

- `discordRoleId` 와 이 값의 정합성(그 역할이 정말 그 스터디 것인지)은 **검증하지 않는다.** 검증하려면
  스터디↔역할 매핑을 Discord 서비스가 들고 있어야 하는데, 그 매핑의 주인은 백엔드다.
- 그러므로 **틀린 값이 와도 400 이 아니다** — snowflake 형식만 맞으면 통과한다. 형식이
  틀리면 400 인데, 이건 정합성 검사가 아니라 로그에 쓰레기가 들어가는 걸 막는 것이다.

### 배정할 수 있는 역할의 범위

봇은 `discordRoleId` 를 **제한하지 않는다** — 길드에 있고 봇이 붙일 수 있는 역할이면 무엇이든 배정한다.
captain 이 스터디 역할이 아닌 역할을 배정하는 것도 허용이다. **의도된 설계다.**

올바른 역할을 고르는 책임은 **백엔드**에 있다:

- 백엔드가 아는 역할은 [`create-study`](create-study.md#성공-응답) 가 만든 것뿐이다.
  그 응답이 `discordStudyId` 와 `discordRoleId` 를 **한 쌍으로** 돌려주므로, 백엔드는 그 쌍을
  저장해 두었다가 이 요청의 `discordStudyId` 와 `discordRoleId` 로 **그대로** 보낸다.
- 그래서 봇은 둘의 정합성을 다시 확인하지 않는다. 신뢰 경계는 `X-API-Key` 가 긋고
  ([common-header.md](common-header.md#x-discord-user-id)), 그 안쪽의 백엔드가 보낸 쌍은 맞는 것으로 본다.
- 잘못된 쌍이 오면 **백엔드 버그**다. 봇은 막지 않고 그대로 배정하며, 추적은 로그에 남긴
  `discordStudyId` · `discordRoleId` 로 한다.

## 성공 응답

**204 No Content** — 바디가 없다.

바디 없는 성공에는 200 이 아니라 204 를 쓴다. 200 + 빈 바디는 호출자가 "파싱할 게 있나?" 를
매번 확인하게 만든다.

**204 는 "요청한 유저 전부가 지금 그 역할을 갖고 있다" 는 뜻이다.** 이번 요청이 실제로 붙였는지,
이미 갖고 있었는지는 구분하지 않는다 — 역할 부여는 [멱등](#부분-실패와-재시도)이라 구분할 이유가 없고,
구분하려면 빈 바디를 포기해야 한다.

## 실패 응답

에러 바디는 현재 FastAPI 기본형 `{"detail": "..."}` 이다
(BE 의 `{errorCode, errorMessage}` 와 다르다 — [미정 사항](#미정-사항) 참고).

### 공통 헤더에서 나는 것

| 상태 | 언제 |
|------|------|
| **400** | `X-Discord-User-ID` 가 없거나 snowflake 형식이 아님 — 이 엔드포인트는 captain 확인 때문에 필수다 |
| **401** | `X-API-Key` 없음 또는 불일치 |
| **403** | 요청자에게 captain 역할이 없음 |
| **404** | `X-Discord-User-ID` 가 그 길드의 멤버가 아님 |
| **409** | 같은 `Idempotency-Key` 로 다른 바디가 옴 |

### 이 엔드포인트에서 나는 것

| 상태 | 언제 | 원인 |
|------|------|------|
| **400** | `discordRoleId` · `discordStudyId` · `discordUserIds` 의 원소가 snowflake 형식이 아님 | 요청자 잘못. 그대로 재시도해도 실패한다 |
| **400** | `discordUserIds` 가 없거나 빈 배열 | 위와 같음. "아무것도 안 함" 을 204 로 돌려주지 않는다 — 호출자 쪽 버그일 가능성이 높다 |
| **400** | `discordUserIds` 가 상한 초과 | 상한은 [미정](#미정-사항) |
| **404** | captain 역할을 길드에서 찾지 못함 | 서버·길드 설정 문제(역할이 지워졌거나 잘못 지정됨). 요청자와 무관하므로 403 이 아니다. `detail` 로 다른 404 와 구분한다 |
| **404** | `discordRoleId` 에 해당하는 역할이 길드에 없음 | 이미 지워졌거나 애초에 없는 ID. 아무 유저도 건드리지 않는다 |
| **404** | `discordUserIds` 중 길드 멤버가 아닌 유저가 있음 | 탈퇴했거나 아직 입장 전. **아무 유저도 건드리지 않는다** — [아래](#부분-실패와-재시도) 참고 |
| **502** | Discord 가 배정을 거부 | 봇 권한 부족(`Manage Roles`), **역할 서열** 문제, 그 밖의 Discord 5xx |
| **503** | 봇 비활성 또는 아직 미연결 | `DISCORD_TOKEN` 미설정, 또는 기동 직후 `is_ready()` 가 아직 False |

503 · 502 는 **재시도 가능**하다. 400 · 401 · 403 은 조건이 바뀌기 전에는 재시도해도 같다.
404 는 그 유저가 길드에 들어오거나 역할이 다시 생기면 통한다.
captain 역할 404 는 호출자가 고칠 수 없다 — 길드의 역할이나 서버 설정을 고쳐야 풀린다.

> **역할 서열(role hierarchy)은 502 지만 재시도해도 소용없다.** Discord 는 봇이 **자기 최상위
> 역할보다 위에 있는 역할**을 남에게 붙이는 걸 막고, 관리형 역할(다른 봇의 역할, 부스터 역할)도
> 붙일 수 없다. 증상은 Discord 의 403 인데 이건 *봇* 설정 문제라 호출자가 고칠 수 없다 —
> 길드에서 봇 역할을 스터디 역할들보다 위로 올려야 풀린다. 502 로 뭉뚱그리되
> **로그에는 서열 문제임을 남긴다**.

> **429 는 밖으로 나가지 않는다.** discord.py 가 레이트 리밋을 내부에서 기다렸다가 재시도하므로,
> 증상은 429 응답이 아니라 **응답이 느려지는 것**으로 나타난다. 이 엔드포인트는 유저 수만큼
> Discord 를 호출하므로(아래) 배열이 길수록 눈에 띈다. 호출자는 넉넉한 타임아웃을 잡는다.

## 부분 실패와 재시도

Discord 에는 "역할을 여러 명에게 한 번에" 가 없다. **유저 한 명당 API 호출 한 번**이다
(`PUT /guilds/{guild}/members/{user}/roles/{role}`). 10명이면 10번 나간다 — 3번째에서 끊기면
2명은 이미 붙어 있다.

**규칙 1 — 먼저 다 확인하고, 그 다음에 붙인다.**
역할과 모든 유저를 길드 캐시에서 먼저 해석한다. 하나라도 없으면 **아무것도 하지 않고 404**.
이러면 "존재하지 않는 유저" 같은 가장 흔한 실패는 부분 적용을 만들지 않는다.

**규칙 2 — 붙이는 도중 실패하면 되돌리지 않는다.**
[`create-study`](create-study.md#부분-실패와-재시도) 와 다른 점이다. 저기서는 실패하면 만든 걸
역순으로 지우지만, 여기서는 **지우면 안 된다** — 그 유저가 *원래부터* 그 역할을 갖고 있었을 수
있고(다른 경로로 이미 배정됨), 롤백이 그걸 뺏는다. 없던 걸 지우는 것과 있던 걸 뺏는 건 다르다.

대신 **실패를 그대로 돌려주고(502), 이미 붙은 유저 ID 를 로그에 남긴다.**

**규칙 3 — 그래서 재시도는 전체 요청을 다시 보내는 것이다.**
역할 부여는 **멱등**이다. 이미 그 역할을 가진 멤버에게 다시 붙여도 Discord 는 204 를 돌려주고
아무 일도 일어나지 않는다 — 이벤트도, 알림도 없다. 그래서 부분 적용 상태에서 같은 요청을
그대로 다시 보내는 게 안전하고, 그게 정상적인 복구 경로다.

**`Idempotency-Key` 는 성공(204)했을 때만 저장한다.** 실패한 요청은 "일어나지 않은 것" 으로
두고, 같은 키로 다시 오면 **다시 실행**한다. 실패를 캐시하면 규칙 3 의 복구가 막힌다.

> 이 엔드포인트에서 `Idempotency-Key` 는 [`create-study`](create-study.md) 때만큼
> 결정적이지 않다 — 연산 자체가 멱등이라 중복 실행이 해롭지 않기 때문이다. 그래도
> [공통 규약](common-header.md#idempotency-key)대로 붙인다: 같은 키에 다른 바디가 오는 걸
> 409 로 잡아주고, 호출자가 엔드포인트마다 다른 규칙을 기억하지 않아도 된다.

## 미정 사항

정해야 이 계약이 확정되는 것들.

- **captain 역할을 찾는 방법** — [`create-study`](create-study.md#미정-사항) 와 같은 결정을 따른다
  (설정값으로 ID 를 받는 쪽 권장).
- **`discordUserIds` 상한** — 유저 수만큼 Discord 호출이 나가므로 상한이 곧 최악의 응답 시간이다.
  100 정도가 무난하지만, 한 스터디 최대 인원이 정해지면 거기 맞추는 게 낫다.
- **길드에 없는 유저 처리** — 지금은 [규칙 1](#부분-실패와-재시도)대로 **전체 404** 다.
  대안은 없는 유저를 건너뛰고 나머지만 붙이는 것인데, 그러면 "누가 빠졌는지" 를 알려야 하고
  **빈 응답 바디를 포기**해야 한다 (207 + 유저별 결과). 어느 쪽인지는 백엔드가 탈퇴 멤버를
  어떻게 다루는지에 달렸다.
- **에러 바디 모양** — 여기는 FastAPI 의 `{"detail": ...}`, 백엔드는 `{errorCode, errorMessage}` 다.
  맞출지 말지는 별도 결정 사항.
