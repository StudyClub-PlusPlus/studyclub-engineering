# Remove Discord Role

역할 하나를 유저 **한 명**에게서 뗀다. 스터디 종료·탈퇴 때 [`assign-role`](assign-role.md) 로
붙였던 역할을 회수하는 용도다. 붙이는 것의 짝이라 계약 대부분이 같고, **다른 곳만** 이 문서에 자세히 적는다.

> ⚠️ **아직 구현 전이다.** 이 문서는 구현할 계약이다.
> 공통 요청 헤더는 [`common-header.md`](common-header.md) 를 따른다.
> **대상 길드는 하나로 고정**이라 요청에 길드를 넘기지 않는다.

## 요청

```
DELETE /api/v1/roles/{discordRoleId}/users/{discordUserId}?discordStudyId={discordStudyId}
```

| 위치 | 이름 | 타입 | 필수 | 설명 |
|------|------|------|------|------|
| 경로 | `discordRoleId` | string | O | 뗄 **Discord 역할 ID**(snowflake). `create-study` 가 돌려준 `discordRoleId` 가 여기 들어간다 |
| 경로 | `discordUserId` | string | O | 역할을 뗄 **Discord 유저 ID**(snowflake) |
| 쿼리 | `discordStudyId` | string | O | snowflake. **로깅·추적용** — [assign-role 과 같다](assign-role.md#discordstudyid-의-역할) |

**바디가 없다.** 그래서 `Content-Type` 도 붙이지 않는다. assign-role 이 바디에 싣던 `discordStudyId` 는
쿼리로 옮겼다.

헤더는 [공통 헤더](common-header.md) 전부 — `Idempotency-Key` 는 **필수**다.

**captain 역할을 가진 멤버만 호출할 수 있다.** [`create-study`](create-study.md#요청) ·
[`assign-role`](assign-role.md#요청) 과 같은 규칙이다 — 없으면 **403**.

모든 ID 는 문자열이고 `^[0-9]{17,20}$` 로 검증한다.

**`discordRoleId` 는 제한하지 않는다.** 올바른 `discordStudyId` · `discordRoleId` 쌍을 보내는 건 백엔드
책임이다 — [assign-role 의 역할 범위](assign-role.md#배정할-수-있는-역할의-범위) 와 같은 신뢰 모델이다.

## 성공 응답

**204 No Content** — 바디가 없다.

**204 는 "그 유저가 지금 그 역할을 갖고 있지 않다" 는 뜻이다.** 이번 요청이 실제로 뗐는지,
원래 없었는지, 유저가 이미 길드를 떠났는지는 구분하지 않는다 — 셋 다 원하는 최종 상태는 같다.

## 실패 응답

에러 바디는 현재 FastAPI 기본형 `{"detail": "..."}` 이다.

### 공통 헤더에서 나는 것

| 상태 | 언제 |
|------|------|
| **400** | `X-Discord-User-ID` 가 없거나 snowflake 형식이 아님 — 이 엔드포인트는 captain 확인 때문에 필수다 |
| **400** | `Idempotency-Key` 없음 |
| **401** | `X-API-Key` 없음 또는 불일치 |
| **403** | 요청자에게 captain 역할이 없음 |
| **404** | `X-Discord-User-ID` 가 그 길드의 멤버가 아님 |

### 이 엔드포인트에서 나는 것

| 상태 | 언제 | 원인 |
|------|------|------|
| **400** | `discordRoleId` · `discordUserId` · `discordStudyId` 가 snowflake 형식이 아님 | 요청자 잘못. 그대로 재시도해도 실패한다 |
| **400** | `discordStudyId` 쿼리가 없음 | 위와 같음 |
| **404** | captain 역할을 길드에서 찾지 못함 | 서버·길드 설정 문제. 요청자와 무관하므로 403 이 아니다. `detail` 로 다른 404 와 구분한다 |
| **404** | `discordRoleId` 에 해당하는 역할이 길드에 없음 | [아래](#역할이-없으면-404-다) 참고 |
| **502** | Discord 가 회수를 거부 | 봇 권한 부족(`Manage Roles`), **역할 서열** 문제, 그 밖의 Discord 5xx |
| **503** | 봇 비활성 또는 아직 미연결 | `DISCORD_TOKEN` 미설정, 또는 기동 직후 `is_ready()` 가 아직 False |

`discordUserId` 가 **길드 멤버가 아니어도 에러가 아니다** (204) — [아래](#길드에-없는-유저는-204-다) 참고.

503 · 502 는 **재시도 가능**하다. 400 · 401 · 403 은 조건이 바뀌기 전에는 재시도해도 같다.
captain 역할 404 는 호출자가 고칠 수 없다 — 길드의 역할이나 서버 설정을 고쳐야 풀린다.

역할 서열(502 지만 재시도로 안 풀림)과 429(밖으로 안 나가고 느려짐)는
[assign-role](assign-role.md#이-엔드포인트에서-나는-것) 과 같다. 서열 제한은 붙일 때와 뗄 때 똑같이 걸린다.

## 여러 명을 뗄 때

한 번에 몇 명 정도를 떼는 것이 예상 사용 패턴이라, 대량 회수용 배열 바디는 두지 않는다.
여러 명이면 **호출자가 유저 수만큼 부른다.**

- 요청마다 **Discord 호출은 한 번**이다 (`DELETE /guilds/{guild}/members/{user}/roles/{role}`).
  그래서 assign-role 의 부분 실패 문제가 요청 안에서는 생기지 않는다 — 떼졌거나, 안 떼졌거나 둘 중 하나다.
- 대신 **부분 실패는 호출자 쪽으로 옮겨간다.** 3명 중 1명이 502 면 나머지 2명은 떼진 상태다.
  호출자는 **실패한 유저만** 다시 부르면 된다 — 각 요청이 독립적이다.
- **한 명이 실패해도 나머지를 계속 부른다.** 멈추면 뒤에 남은 유저들이 재시도가 올 때까지 계속
  접근권을 가진다. 이미 뗀 유저에게 역할을 다시 붙여 "되돌리지" 않는다 — 방금 뗀 사람에게 접근권을
  다시 주는 건 회수 요청의 의도와 정반대다.
- **`Idempotency-Key` 는 유저마다 따로** 만든다 — 로그에서 유저별 요청을 구분하기 위해서다.
  재시도할 때는 그 유저의 원래 키를 다시 보낸다.
- 역할 회수는 **멱등**이다 — 역할이 없는 멤버에게서 떼도 Discord 는 204 를 돌려준다. 그래서 응답을 못 받은
  요청은 같은 키로 그대로 다시 보내면 된다. 서버는 중복 요청을 막지 않는다 ([assign-role](assign-role.md#부분-실패와-재시도) 과 같다).

## assign-role 과 다른 점

뗄 때는 **실패의 방향**이 반대다. 붙이다 실패하면 누군가 접근을 *못 얻고*, 떼다 실패하면 누군가
접근을 *잃지 않는다*. 탈퇴한 사람이 스터디 채널을 계속 보는 쪽이 더 나쁜 실패이므로,
아래 규칙은 "**확실히 떼는 것**" 쪽으로 기울어 있다.

### 길드에 없는 유저는 204 다

assign-role 은 길드에 없는 유저가 있으면 404 다. 여기서는 **성공으로 친다.**

- Discord 에서 멤버가 길드를 나가면 멤버 객체가 사라지고, 다시 들어와도 **역할은 복원되지 않는다.**
  길드에 없는 유저는 이미 그 역할이 없다 — 원하는 상태가 이미 이뤄져 있다.
- 역할 회수가 필요한 가장 흔한 경우가 **탈퇴**다. 이걸 404 로 돌려주면 호출자는 "이미 나간 사람" 과
  "잘못 보낸 요청" 을 구분해서 처리해야 한다. 어느 쪽이든 할 일이 없으므로 204 로 합친다.
- **판단은 캐시가 아니라 Discord 응답으로 한다.** Discord 에 회수 요청을 보내고, `Unknown Member` 로
  답하면 204 를 돌려준다(로그에는 남긴다). 캐시로 "없음" 을 판정하면 캐시에서 빠진 *실제 멤버*에게서
  역할을 떼지 않고 204 를 돌려주게 되는데, 그건 역할이 남아 있는데 성공이라고 말하는 것이다.
  assign-role 에서 캐시 누락은 시끄러운 404 로 끝나지만, 여기서는 **조용한 거짓 성공**이 된다.

### 역할이 없으면 404 다

"역할이 없으면 누구도 그 역할을 갖고 있지 않으니 204" 라는 논리도 가능하다. 그래도 404 로 둔다 —
**틀린 `discordRoleId`** (백엔드 버그) 도 같은 증상이라, 204 로 넘기면 백엔드는 잘못된 ID 로 회수가
계속 "성공" 하는 걸 알아챌 방법이 없다. 스터디 역할이 길드에서 지워진 경우라면 백엔드가 404 를
보고 그 스터디를 정리하면 된다.

역할은 요청 전에 확인하므로, 역할이 없을 때는 Discord 에 회수 요청을 보내지 않는다.

## 미정 사항

정해야 이 계약이 확정되는 것들.

- **에러 바디 모양** — 여기는 FastAPI 의 `{"detail": ...}`, 백엔드는 `{errorCode, errorMessage}` 다.
  맞출지 말지는 별도 결정 사항.
