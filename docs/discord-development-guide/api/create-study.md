# Create Study

스터디 하나를 Discord 길드에 만든다. 카테고리 1개 + 그 아래 기본 채널 2개(텍스트·음성) +
전용 역할 1개를 한 요청으로 생성한다.

> ⚠️ **아직 구현 전이다.** 이 문서는 구현할 계약이다.
> 공통 요청 헤더는 [`common-header.md`](common-header.md) 를 따른다.
> **대상 길드는 하나로 고정**이라 요청에 길드를 넘기지 않는다 — 길드를 어떻게 지정할지는
> 별도 컨텍스트에서 다룬다.

## 요청

```
POST /api/v1/studies
```

헤더는 [공통 헤더](common-header.md) 전부 — `Idempotency-Key` 는 **필수**다
(로그 추적용이다. 중복 요청은 키가 아니라 `studyName` 으로 막는다 — [중복 요청](#중복-요청) 참고).

**captain 역할을 가진 멤버만 호출할 수 있다.** 봇이 `X-Discord-User-ID` 로 길드 멤버를 조회해
captain 역할 보유 여부를 확인하고, 없으면 **403** 이다. captain 역할은 길드에 **이미 존재하는**
역할이다 — 이 엔드포인트가 만들지 않고, 찾지 못하면 만들지 말고 실패해야 한다
(없는 역할을 새로 만들면 아무 검사도 하지 않는 것과 같아진다).

```jsonc
{ "studyName": "알고리즘 스터디" }
```

| 필드 | 타입 | 필수 | 제약 |
|------|------|------|------|
| `studyName` | string | O | 1–100자. 카테고리·역할 이름에 그대로 쓰이므로 Discord 의 채널/역할 이름 한도(100자)를 따른다 |

만드는 것은 순서대로 네 개다:

1. `studyName` 이름의 **카테고리**
2. 그 아래 **텍스트 채널** 1개 (기본 이름 — [미정](#미정-사항))
3. 그 아래 **음성 채널** 1개 (기본 이름 — [미정](#미정-사항))
4. 스터디 전용 **역할** 1개

## 성공 응답

**201 Created** — 리소스를 만드는 요청이므로 200 이 아니라 201 이다.

```jsonc
{
  "discordStudyId": "1327394882193883136",
  "discordRoleId": "1327394882193883140"
}
```

| 필드 | 타입 | 설명 |
|------|------|------|
| `discordStudyId` | string | 생성된 **카테고리의 Discord 채널 ID**(snowflake) |
| `discordRoleId` | string | 생성된 **역할의 Discord 역할 ID**(snowflake) |

이름에 `discord` 를 붙인 건 **StudyClub++ 쪽 ID 가 아니라 Discord 쪽 ID** 임을 못 박기 위해서다.

**둘 다 문자열이다** — snowflake 는 64비트라 JSON 숫자로 내보내면 JS 호출자에서 정밀도가
깨진다 ([common-header.md](common-header.md#x-discord-user-id) 와 같은 규칙).

생성된 **텍스트·음성 채널 ID 는 응답에 넣지 않는다.** 백엔드가 필요해지면 그때 조회한다.

## 실패 응답

에러 바디는 현재 FastAPI 기본형 `{"detail": "..."}` 이다
(BE 의 `{errorCode, errorMessage}` 와 다르다 — [미정 사항](#미정-사항) 참고).

### 공통 헤더에서 나는 것

| 상태 | 언제 |
|------|------|
| **400** | `X-Discord-User-ID` 가 없거나 snowflake 형식이 아님 — 이 엔드포인트는 captain 확인 때문에 필수다 |
| **400** | `Idempotency-Key` 없음 |
| **401** | `X-API-Key` 없음 또는 불일치 |
| **403** | 요청자에게 captain 역할이 없음 |
| **404** | `X-Discord-User-ID` 가 그 길드의 멤버가 아님 |

### 이 엔드포인트에서 나는 것

| 상태 | 언제 | 원인 |
|------|------|------|
| **400** | `studyName` 누락·공백·100자 초과 | 요청자 잘못. 그대로 재시도해도 실패한다 |
| **404** | captain 역할을 길드에서 찾지 못함 | 서버·길드 설정 문제(역할이 지워졌거나 잘못 지정됨). 요청자와 무관하므로 403 이 아니다. `detail` 로 멤버 404 와 구분한다 |
| **409** | 같은 `studyName` 의 스터디가 이미 있거나 만드는 중임 | 중복 요청 차단. SQLite 예약과 Discord 의 동명 카테고리로 판단한다 — [중복 요청](#중복-요청) 참고. Discord 자체는 동명 카테고리를 허용하므로 직접 확인해야 한다 |
| **502** | Discord 가 생성을 거부 | 봇 권한 부족(`Manage Channels` / `Manage Roles`), 길드 한도 초과(채널 500개, 역할 250개), 그 밖의 Discord 5xx |
| **503** | 봇 비활성 또는 아직 미연결 | `DISCORD_TOKEN` 미설정, 또는 기동 직후 `is_ready()` 가 아직 False |

503 · 502 는 **재시도 가능**하다. 400 · 401 · 403 · 404 는 조건이 바뀌기 전에는 재시도해도 같다.
captain 역할 404 는 호출자가 고칠 수 없다 — 길드의 역할이나 서버 설정을 고쳐야 풀린다.

> **429 는 밖으로 나가지 않는다.** discord.py 가 레이트 리밋을 내부에서 기다렸다가 재시도하므로,
> 증상은 429 응답이 아니라 **응답이 느려지는 것**으로 나타난다. 호출자는 넉넉한 타임아웃을 잡는다.
> 타임아웃으로 끊고 재시도하면 첫 요청이 아직 처리 중이거나 이미 끝나 **409** 를 받을 수 있다
> ([아래](#부분-실패와-재시도) 참고).

## 중복 요청

이 API 에서 중복 실행의 영향이 가장 큰 곳이다 — 카테고리·채널·역할이 두 벌 생기고, 백엔드는 그중 한 벌의
ID 만 저장한다. 그래서 이 엔드포인트만 **`studyName` 으로 중복을 막는다.** `Idempotency-Key` 는
[로그용](common-header.md#idempotency-key)이라 중복을 막지 않는다.

Discord 에 같은 이름의 카테고리가 있는지만 물어보면 **동시에 온 두 요청**(더블 클릭 등)을 못 막는다 —
둘 다 "아직 없음" 을 보고 둘 다 만든다. 그래서 만들기 전에 이름을 **SQLite 에 먼저 예약**한다
(Python 표준 라이브러리 `sqlite3` 라 새 의존성은 없다).

| 컬럼 | 설명 |
|------|------|
| `study_name` | UNIQUE. 요청의 `studyName` 그대로 |
| `status` | `PROCESSING` · `COMPLETED` |
| `idempotency_key` | 이름을 잡고 있는 요청 — 로그 추적용 |

처리 순서:

1. 헤더 · 바디 · captain 역할을 먼저 검증한다. 여기서 실패하면 예약하지 않는다.
2. `status = PROCESSING` 으로 **INSERT** 한다. UNIQUE 위반이면 **409** — 상대 행이 `PROCESSING` 이든
   `COMPLETED` 든 같다. INSERT 한 문장이 검사와 예약을 겸하므로 동시에 온 두 요청 중 하나만 통과한다.
3. 길드에 같은 이름의 카테고리가 있는지 확인한다. 있으면 **행을 지우고 409** — SQLite 도입 전에 만들었거나
   길드에서 직접 만든 카테고리는 SQLite 에 없기 때문이다.
4. 네 개를 만든다.
5. 넷 다 성공하면 `status = COMPLETED` 로 **UPDATE** 하고 201 을 돌려준다.

실패했을 때 예약 행은:

- **생성이 실패하고 정리(rollback)까지 끝나면 지운다.** 일어나지 않은 요청이므로 같은 이름으로 다시 만들 수 있어야 한다.
- **정리까지 실패하면 `PROCESSING` 으로 남긴다.** 길드에 그 이름의 고아 리소스가 남아 있으니, 수동 정리 전까지
  같은 이름을 막는 게 맞다. 수동 정리할 때 행도 같이 지운다.

## 부분 실패와 재시도

이 엔드포인트는 Discord 를 **네 번** 호출한다. 2번째(텍스트 채널)에서 실패하면 카테고리는 이미
만들어져 있다 — 아무것도 안 하면 이름만 있는 빈 카테고리가 길드에 남는다.

**규칙: 한 단계라도 실패하면 그 요청에서 만든 것을 역순으로 지우고 에러를 돌려준다.**
성공은 넷 다 됐을 때뿐이다. 중간 상태를 성공으로 돌려주지 않는다.

- **정리(rollback)까지 실패하면** — 502 를 돌려주되, 남은 카테고리·채널·역할 ID 를 **로그에 남긴다**.
  이건 수동 정리가 필요한 상태이고, 조용히 넘어가면 길드에 고아 리소스가 쌓인다.
  예약 행은 남겨 같은 이름을 막는다 ([중복 요청](#중복-요청) 참고).
- **실패 후 정리까지 끝난 요청은 "일어나지 않은 것"이다.** 예약 행도 지우므로 같은 요청을 다시 보내면
  **다시 실행**된다.
- **응답을 못 받은 호출자가 재시도하면 409 를 받을 수 있다.** 네트워크가 끊겼을 뿐 서버는 넷 다 만들었거나
  아직 만드는 중인 경우다. 스터디가 두 벌 생기지는 않지만, 409 응답에는 기존 ID 가 없어 백엔드가
  `discordStudyId` · `discordRoleId` 를 받을 방법이 없다 — [미정 사항](#미정-사항) 참고.

## 미정 사항

정해야 이 계약이 확정되는 것들.

- **captain 역할을 찾는 방법** — 설정값(예: `DISCORD_CAPTAIN_ROLE_ID`)으로 **ID 를 받는 쪽을 권장**한다.
  `DISCORD_BOT_OUTPUT_CHANNEL` 과 같은 방식이다. 이름으로 찾으면 길드에서 역할 이름을 바꾸거나
  같은 이름의 역할이 하나 더 생길 때 조용히 깨진다.
- **기본 채널 이름** — 텍스트·음성 채널을 무엇으로 부를지 (`일반`/`잡담`, `음성`/`스터디룸` 등).
- **응답을 잃은 뒤 재시도가 409 일 때** — 스터디는 만들어졌는데 백엔드가 ID 를 받지 못한다. 409 바디에 기존
  `discordStudyId` · `discordRoleId` 를 실을지, 수동으로 복구할지 결정 필요.
- **예약 행 정리** — 생성 도중 서비스가 죽으면 행이 `PROCESSING` 으로 남아 그 이름이 계속 막힌다. 스터디 삭제
  API 가 없어서, 길드에서 지운 스터디의 `COMPLETED` 행도 남는다. 오래된 `PROCESSING` 을 풀지, 누가 어떻게 지울지 결정 필요.
- **SQLite 파일 위치** — 컨테이너를 다시 띄워도 남도록 볼륨에 둬야 한다. 경로와 볼륨 설정은 배포 설정에서 정한다.
- **에러 바디 모양** — 여기는 FastAPI 의 `{"detail": ...}`, 백엔드는 `{errorCode, errorMessage}` 다.
  맞출지 말지는 별도 결정 사항.
