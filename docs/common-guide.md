# Common Development Guide

## 기존 API 활용 원칙

새 API 를 만들기 전에 **기존 엔드포인트로 해결 가능한지 먼저 확인**한다.

### 체크리스트

1. 필요한 데이터가 이미 제공되는 API 가 있는가?
2. 기존 API 에 파라미터(필터, 페이징 등)를 추가하면 되는가?
3. 기존 API 의 응답 필드를 확장하면 되는가?

위 세 가지 모두 아닐 때만 새 엔드포인트를 추가한다.

### 이유

- API 수가 늘어나면 문서화, 테스트, 유지보수 비용이 기하급수적으로 증가
- 프론트에서 호출 지점이 분산되면 데이터 정합성 관리가 어려움
- 기존 API 확장이 클라이언트 캐싱/상태 관리에도 유리

### 예시

```
❌ GET /studies/{id}/members  (새 엔드포인트)
   → 스터디 상세에 멤버 목록이 필요할 뿐이라면

✅ GET /studies/{id} 응답에 members 필드 추가
   → 기존 API 확장으로 해결
```

```
❌ GET /my-studies  (새 엔드포인트)
   → 내가 참여한 스터디 목록이 필요할 뿐이라면

✅ GET /studies?memberId=me  (기존 API 에 필터 추가)
```

### BE/FE 공통 적용

- **BE**: 새 컨트롤러/엔드포인트 추가 전에 기존 것 확인. PR 에서 "기존 API 로 안 되는 이유" 명시.
- **FE**: API 호출 시 이미 fetch 하고 있는 데이터에서 꺼낼 수 있는지 먼저 확인. 불필요한 추가 호출 금지.
