# 「모집 중인가」 같은 판정은 서버가 내려주고, 화면은 그 값을 그린다

## 미리 알아야 할 것

| 단어 | 뜻 |
|---|---|
| **API 응답** | 화면(프론트)이 서버(백엔드)에 물어보면 서버가 돌려주는 데이터 |
| **판정** | 여러 값과 규칙을 조합해서 나오는 결론. 예: 마감 시각·정원·인원을 보고 「지금 모집 중이다」 |
| **재료** | 판정에 쓰이는 값. 마감 시각, 정원, 지금 인원 같은 것 |
| **엔티티 메서드** | 서버 코드 안에서 규칙을 계산하는 함수. 판정 규칙은 여기 한 곳에 둔다 |
| **정원 인원** | 정원과 비교하는 사람 수. 10-02 결정으로 「기수 명부의 활성(`ACTIVE`) 인원」이다 ([POL-0004](../../01-planning/_registry/policies/POL-0004-application.md)) |

## 한 줄 요약

모집 중인지 · 정원이 찼는지 · 출석률 · 할 수 있는지 같은 **판정은 서버가 계산해서 응답에 넣는다.**
화면은 받은 값을 그대로 보여주고, 날짜나 숫자로 **다시 계산하지 않는다.**

## 비유

시험 점수표를 생각해 보자. 채점은 선생님 한 분이 기준표 하나로 한다.
학생마다 자기 답안을 보고 직접 채점하면, 같은 답안이 어떤 교실에서는 합격이고 어떤 교실에서는 불합격이 된다.
판정을 화면마다 다시 하는 것이 이와 같다.

## 왜 — 지금 뭐가 문제인가

「정원이 찼나」 하나를 세 곳이 세 가지 방법으로 세고 있었다 (2026-10-09 확인).

| 어디 | 세는 것 |
|---|---|
| 신청 버튼을 누를 때 (신청 API) — **정답** | 기수 명부의 활성 인원 |
| 사이트 스터디 목록·상세 | 최신 모집 회차의 신청서 수 — 정책이 바뀌기 전 기준 |
| 백오피스 목록 초안 (PR #204) | 명부의 활성 + 쉬는 중 인원. 그리고 화면이 마감을 날짜만 보고 다시 비교 |

그래서 이런 일이 생길 수 있었다.

- 정원 10명, 활성 9명 + 쉬는 중 1명인 스터디 → 신청은 **받는데** 백오피스는 **마감**이라고 보여준다
- 마감이 10/31 12:00(한국 시각)이면 백오피스는 다음 날 09:00 까지 **모집중**으로 보여준다 — 화면이 날짜만, 그것도 영국 기준(UTC) 날짜로 비교해서

## 정해진 것

1. 판정은 **서버의 엔티티 메서드 하나**가 계산한다
2. 그 판정이 필요한 **모든 응답**(사이트용·백오피스용·목록·상세)이 같은 메서드를 부르고, 재료도 **같은 방법으로 센다**
3. 응답에 판정 필드를 넣는다 (`recruitStatus` 처럼). 재료(마감 시각, `18/20`)는 보여주기용으로 같이 줄 수 있다
4. 화면에 판정이 필요한데 응답에 없으면, 화면에서 만들지 않고 **스펙에 필드를 추가해 백엔드에 요청**한다
5. 화면이 해도 되는 것: 날짜·숫자 표시 형식, 받은 값으로 정렬·필터, 입력 중 미리 알려주기(최종은 서버)

규칙 전문: [엔드포인트 규약 §판정은 서버가 내려준다](../backend-development-guide/api/endpoint-convention.md#판정은-서버가-내려준다)

## 영향 — 누가 무엇을 해야 하나

- **백엔드:** 새 API 스펙을 쓸 때 판정 필드를 응답 표에 넣는다. 사이트 목록·상세의 정원 인원을 신청 API 와 같은 기준으로 바꾸는 작업이 남아 있다 (POL-0004 「백엔드와 어긋난 것」)
- **프론트:** 판정을 계산하는 코드를 보면 응답 필드로 바꾼다. 필드가 없으면 `// TODO(api)` 를 남기고 요청한다. 공유 함수(`packages/mock` 의 `recruitState()` 등)에 판정 조건을 더하지 않는다
- **에이전트:** `AGENT.md` · `/spec` · `/self-review` 에 이 규칙이 들어갔다. 스펙 작성·리뷰와 PR 전 셀프 리뷰에서 자동으로 확인한다
- **기획:** 할 일 없음. 화면끼리 상태가 다르게 보이면 이 규칙이 깨진 것이니 알려 주면 된다
