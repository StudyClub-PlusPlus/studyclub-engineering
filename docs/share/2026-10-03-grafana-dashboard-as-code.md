# Grafana 대시보드를 레포에서 관리하기로 — 고치는 건 그대로, 저장은 PR 로

> **한 줄** — 대시보드 2개(`스터디클럽 로그` · `스터디클럽 메트릭`)가 이제 레포의
> `observability/dashboards/*.json` 을 정본으로 씁니다. **Grafana 화면에서 고치는 건 그대로
> 됩니다.** 다만 고친 것을 PR 로 올려야 남고, 안 올리면 다음 배포에 덮입니다.

## 미리 알아야 할 것

- **Grafana** — 서버 상태(요청 수·에러율·응답시간)와 로그를 브라우저에서 보는 도구입니다.
  서버에 SSH 로 들어가지 않고도 "지금 무슨 일이 났나" 를 볼 수 있습니다.
- **대시보드(dashboard)** — 그래프 여러 개를 한 화면에 모아 둔 것. 지금 두 개가 있습니다.
  로그용(3개 패널) · 메트릭용(16개 패널).
- **패널(panel)** — 대시보드 안의 그래프 하나하나.
- **데이터소스(datasource)** — 그래프가 숫자를 읽어오는 창고. 메트릭은 **Prometheus**,
  로그는 **Loki** 라는 창고에서 읽습니다.
- **프로비저닝(provisioning)** — 사람이 화면에서 클릭해 만드는 대신, **파일을 보고 자동으로**
  설정을 만들어 넣는 방식. "설정을 코드로 관리한다" 와 같은 말입니다.

## 왜 바꿨나

지금까지 대시보드는 **Grafana 안에만** 있었습니다. 이게 왜 문제인지 비유하면 —
**가게 영업시간을 문에 붙인 종이 한 장에만 써 둔 것**과 같습니다. 종이가 떨어지면
영업시간이 없어진 게 아니라 **아무도 모르게 됩니다.** 손님은 그냥 헛걸음을 하고,
가게는 손님이 안 왔다고만 생각합니다.

Grafana 도 똑같습니다. 서버가 재시작되거나 설정이 날아가면 대시보드와 알림이 사라지는데,
**사라진 뒤의 화면은 "아무 문제 없는 평온한 하루" 와 똑같이 생겼습니다.** 알림이 안 오는 게
정상인지 고장인지 구분이 안 됩니다. 그래서 정본을 레포(=복사본이 여러 군데 남고, 바뀐 이력이
전부 기록되는 곳)로 옮겼습니다.

## 옮기면서 발견한 것 — 사실은 지금도 반쯤 고장이었다

| 대시보드 | 무슨 상태였나 |
|---|---|
| 스터디클럽 메트릭 | 창고 주소가 **39곳에 그 Grafana 전용 값으로 박혀** 있었습니다. 다른 Grafana 로 옮기면 패널 16개가 **전부 빈 화면**이 됩니다 |
| 스터디클럽 로그 | 창고를 아예 안 적어 뒀습니다. "기본 창고를 써라" 는 뜻인데, 지금 기본 창고가 **우연히** Loki 라서 돌고 있었습니다. 기본이 Prometheus 인 환경에서는 로그 질문을 메트릭 창고에 던집니다 |

둘 다 **에러가 전혀 안 납니다.** 옮겨 넣으면 "성공" 이라고 나오고 대시보드도 목록에
보입니다. 패널만 비어 있습니다. 그래서 필요한 날(=장애가 난 날) 처음 알게 됩니다.

고친 방법은 **창고 주소를 직접 쓰지 않고 "이 대시보드가 쓸 창고" 라는 선택 항목으로 바꾼 것**
입니다. 대시보드 왼쪽 위에 창고를 고르는 드롭다운이 하나 생겼고, 어느 Grafana 에 올려도
그 환경의 창고를 알아서 집습니다.

## 여러분이 체감할 변화

### 1. 고치는 방법은 그대로입니다 — Grafana 화면에서

패널을 추가하고 쿼리를 바꾸고 숫자가 어떻게 나오는지 **보면서** 작업하세요. 이걸 막는 건
고려했다가 접었습니다. 막으면 "레포에 먼저 쓰고 → 머지하고 → 그다음에 확인" 이라는
거꾸로 된 순서를 강요하게 되는데, 그래프는 눈으로 봐야 맞는지 아는 물건입니다.

### 2. 다 됐으면 PR 로 올려야 남습니다

```
Grafana 에서 고친다  →  숫자 확인  →  export  →  PR  →  머지되면 배포
```

올리는 사람이 할 일은 `observability/README.md` 의 절차 세 줄입니다 — export 하고,
`--normalize` 로 정리하고, `--lint` 로 검사하고 PR. 검사가 위에 적은 함정(창고 주소 박힘,
변수명 오타 등)을 **머지 전에** 잡습니다.

### 3. ⚠️ 올리지 않으면 다음 배포에 덮입니다

레포가 정본이므로, 배포가 돌 때 레포 내용이 Grafana 를 덮어씁니다. **Grafana 에서 고치고
PR 을 안 올린 변경은 그때 사라집니다.**

이게 이 방식의 유일한 대가라서, 안전장치를 하나 뒀습니다 — **배포 직전에 "Grafana 쪽에
레포에 없는 변경이 있는지" 먼저 검사**합니다(drift 검사). 어긋나면 알 수 있습니다.

> **실험만 하고 버릴 거면** Grafana 에서 「Save as copy」로 사본을 만들어 거기서 하세요.
> 사본은 레포가 관리하지 않으니 덮이지 않습니다.

### 4. 알림 규칙 11개는 아직 그대로입니다

[서버 이상을 디스코드로 알린다](2026-09-28-grafana-alert-discord-bot.md) 에서 만든 **알림 규칙
11개**는 **여전히 Grafana 안에만** 있습니다. 같은 방식으로 옮길 예정이지만, 그쪽은 자동화에 쓸
전용 계정 토큰이 필요해서 순서를 뒤로 뒀습니다. 규칙을 추가하는 절차는 그대로입니다 —
[`docs/observability/adding-alerts.md`](../docs/observability/adding-alerts.md).

## 정해진 규약 하나 — 대시보드에는 `${VAR}` 를 쓰지 않습니다

알림 설정에서는 환경마다 다른 값(채널 ID 등)을 `${VAR}` 로 비워 두고 자동 채우기로
처리하기로 했었습니다. **대시보드에서는 그 방법을 쓸 수 없습니다** — Grafana 자신이
`$이름` 문법을 변수로 쓰고 있어서, 검사 도구가 "아직 안 채워진 자리" 와 "Grafana 변수" 를
구분할 방법이 없습니다.

대신 **더 센 검사**를 넣었습니다. 파일 안의 모든 `$이름` 이 그 대시보드에 선언된 변수이거나
Grafana 가 기본 제공하는 변수여야 하고, 아니면 검사가 실패합니다. 덤으로 **변수명 오타까지**
잡힙니다 (Grafana 는 모르는 변수를 조용히 빈 문자열로 바꿔 버리고 경고하지 않습니다).

## 묻고 싶은 것

1. **어긋난 걸 발견했을 때 배포를 멈출까요, 경고만 할까요?** 누군가 Grafana 에서 고치고
   PR 을 안 올린 상태에서 배포가 돌면, 그 변경이 사라집니다.
   - **멈춘다** — 안전하지만, 남의 미처리 변경 때문에 내 배포가 막힙니다
   - **경고만 하고 덮는다** — 배포가 안 막히지만, 경고를 놓치면 그대로 사라집니다

   저는 **처음엔 경고만** 쪽입니다(지금 대시보드가 2개라 사고 규모가 작습니다). 한 번이라도
   실제로 날아가면 멈추는 쪽으로 바꾸는 게 맞다고 봅니다. 의견 주세요.
2. **지금 두 대시보드에 없어서 아쉬운 패널이 있나요?** 이번에 옮기면서 **내용은 하나도 안
   바꿨습니다.** 추가·수정은 다음 PR 에서 받습니다.
3. **대시보드를 새로 만들 계획이 있는 분?** 만들기 전에 알려주시면 처음부터 레포 쪽으로
   받겠습니다. 다 만든 뒤에 옮기면 위에 적은 함정을 다시 치우게 됩니다.
