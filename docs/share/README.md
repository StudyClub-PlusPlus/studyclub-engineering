# share — 팀에 물어보거나 알려야 할 것

작업하다 **팀원의 결정·답변이 필요하거나, 정해져서 팀이 알아야 하는 것**을 여기 한 건씩 쌓는다.
코드 주석이나 PR 설명에만 있으면 머지되는 순간 아무도 안 읽는다.

## 무엇을 담나

| 담는다 | 안 담는다 |
|---|---|
| 팀원에게 **물어야 하는 것** (정책·기획 확인, 값 요청) | 구현 방법 논의 (PR 리뷰에서) |
| **결정된 것** 중 다른 작업이 따라야 하는 것 (경로 규약·권한 정책·이름 규칙) | 한 번 쓰고 마는 선택 |
| 뒤집힌 전제 — "이럴 줄 알았는데 아니었다" | 버그 수정 내역 (커밋이 말한다) |

2주 넘게 그대로 쓰이면 [`../adr/`](../adr/README.md) 로 올린다 (이 파일은 지우지 않고 맨 위에 `→ ADR NNNN`). 여기는 **굳기 전**과 **굳었다는 사실**이 머무는 곳이다.

---

## 쓰는 법 — 아무것도 모르는 사람이 읽는다고 가정한다 (필수)

**이 폴더의 독자는 그 작업을 안 한 사람이다.** 기획자·디자이너·이번 주에 합류한 개발자·
세 달 뒤의 나. 그 사람들은 배경을 모른다. **배경을 모르는 채로 읽어도 끝까지 이해되게 쓴다.**

### 다섯 가지 규칙

1. **맨 앞에 「미리 알아야 할 것」을 둔다.** 본문에 나오는 단어와 상황을 두세 줄로 먼저 푼다.
   이 칸이 없으면 독자는 첫 문단에서 멈춘다
2. **약어·전문용어는 처음 나올 때 풀어 쓴다.** `API` → "프로그램끼리 정보를 주고받는 창구",
   `엔드포인트` → "그 창구의 주소". 한 번 풀었으면 그다음부터는 그냥 써도 된다
3. **비유를 하나 넣는다.** 추상적인 구조는 그림이나 일상 비유 하나가 세 문단을 이긴다
4. **문장을 짧게.** 한 문장에 한 가지. 쉼표로 이어 붙이지 않는다
5. **"그래서 나는 뭘 해야 하나"로 끝낸다.** 읽는 사람이 자기 할 일을 찾을 수 있어야 한다

### 셀프 체크 한 줄

> **이 프로젝트를 오늘 처음 본 사람이 읽고, 무슨 일이 왜 정해졌는지 말할 수 있나.**

아니라면 아직 덜 쓴 것이다.

## 파일 만들기

파일 하나에 한 건. 이름은 `YYYY-MM-DD-<한-줄-주제>.md`. 만들면 아래 [목록](#목록)에 한 줄 추가하고 공유 칸은 `공유전` — [공유](#공유--모아서-한-번에).

```markdown
---
상태: 질문 | 결정됨 | 보류
물어볼 사람: <역할> (예: 기획)
반영:                  ← 결정됨이면 필수. 이 결정으로 고칠 문서와 그 상태
  - specs/<도메인>/spec.md — 안 됨
  - 01-planning/stories/<이름>/PRD.md — 됨 (#PR)
---

# <한 줄 제목>

## 미리 알아야 할 것      ← 필수. 용어와 배경을 먼저 푼다
## 한 줄 요약             ← 결론부터. 근거는 뒤에
## 왜 — 지금 뭐가 문제인가
## 정해진 것 (또는 물어볼 것)
## 영향 — 누가 무엇을 해야 하나
```

## 공유 — 모아서 한 번에

**한 건씩 바로 알리지 않는다.** 팀이 자주 끊기지 않게 쌓아 두었다가 모아서 한 번에 알린다.

| 공유 칸 | 뜻 |
|---|---|
| `공유전` | 문서는 올라갔지만 아직 팀에 알리지 않았다. **새 건은 항상 이 값으로 목록에 추가한다** |
| `공유됨 (MM-DD)` | 그날 팀 채널에 알렸다. 2026-10-09 이전 건은 날짜 없이 `공유됨` |

알릴 때 순서:

1. 목록에서 `공유전` 인 건을 모은다
2. 한 메시지로 팀에 알린다 — 건마다 제목 한 줄 + 링크 + "누가 무엇을 해야 하나" 한 줄
3. **같은 PR(또는 커밋)에서** 그 건들의 공유 칸을 `공유됨 (MM-DD)` 로 바꾼다 — 알린 사실도 레포에 남아야 다음 사람이 무엇이 남았는지 안다

`상태` 칸(질문 · 결정됨 · 보류)과 `공유` 칸은 따로 움직인다. 질문 건도 공유해야 답이 온다.

## 반영 — 결정이 기획 문서에 들어갔나

결정이 났어도 PRD · POL · 스펙 · ERD 가 그대로면, 개발자는 옛 문서를 보고 만든다.
그래서 **결정마다 고칠 문서를 적고, 고쳤는지 표시한다.** 공유 칸과 같은 방식이다.

| 반영 칸 | 뜻 |
|---|---|
| `됨` | 고칠 문서를 모두 고쳤다 |
| `일부 (<문서>)` | 괄호 안 문서가 아직 옛 내용이다 |
| `안 됨` | 고칠 문서를 하나도 고치지 않았다 |
| `확인 필요` | 문서와 결정이 달라 보이는데, 어느 쪽이 맞는지 정해야 한다 |
| `해당 없음` | 코드 규약·운영처럼 기획 문서와 무관한 결정 |
| `결정 전` | 상태가 `질문` 이다 |

1. `결정됨` 으로 바꿀 때 **파일 머리의 `반영:` 에 고칠 문서를 적는다.** 처음엔 `안 됨` 이어도 된다
2. 그 문서를 고치는 **같은 PR 에서** 해당 줄을 `됨 (#PR)` 로, 목록의 반영 칸도 맞게 바꾼다
3. 고친 문서 쪽에는 바뀐 줄 끝에 `(→ [share MM-DD](../../docs/share/...))` 처럼 이 파일을 건다 — 왜 바뀌었는지 문서에서 바로 찾게
   - **고친 문서가 Story PRD 면 PRD 머리(「기준 프로토타입」 아래)의 `관련 결정:` 줄에도 건다** — `관련 결정: [MM-DD 제목](../../../docs/share/...) · …`.
     개발자가 PRD 한 장만 열어도 이 화면에 걸린 결정을 다 찾는다. 할 일 자체는 PRD 본문 · §3 「개발 범위」에 적고, share 는 「왜」를 찾아가는 링크다
   - 이미 만든 코드를 고쳐야 하는 결정이면 그 PRD 「개발 범위」의 「할 일」 칸에 적는다 — share 의 「이미 개발된 것 중 바뀐 것」과 같은 내용
4. **개발자는 목록에서 반영 칸이 `됨`·`해당 없음` 이 아닌 건만 보면 된다.** 나머지는 이미 PRD·스펙에 들어가 있다

2026-10-12 이전 건은 그날 문서를 대조해 채운 값이다. 고친 문서 쪽 링크(3번)는 소급하지 않는다.
