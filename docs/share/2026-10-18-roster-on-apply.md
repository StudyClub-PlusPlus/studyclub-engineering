# 신청하면 명부에 바로 들어간다 — 반은 비워 두고 캡틴이 나중에 채운다

## 미리 알아야 할 것

- **신청서**(`STUDY_APPLICATION`): 크루가 낸 신청 폼. 「무엇을 적어 냈나」를 담는다.
- **명부**(`STUDY_PARTICIPANT`): 그 스터디에 실제로 참여하는 사람 목록. 출석부 · 정원 · 내 스터디 · 참여 명단이 모두 이 표를 읽는다.
- **반**(`STUDY_GROUP`): 한 스터디 안에서 모이는 시간이 다른 묶음 (「A반」, 「미국 금요일반」). 캡틴이 **신청자를 보고 나서** 만든다 ([반 편성 PRD](../../01-planning/stories/captain-assign-classes/PRD.md) 「반은 모집 전에 만들 수 없다」).
- **PRD**: 화면 기획 문서. **스펙**: 서버 API 약속 문서. 둘은 같은 말을 해야 한다.
- **트랜잭션**: 여러 저장을 「전부 되거나, 전부 안 되거나」로 묶는 것.
- 비유하면 신청은 **학원 등록**이다. 등록하는 순간 학생 명단에 이름이 올라간다. 몇 반에 갈지는 반 편성 날 정한다. 반이 정해지기 전에도 그 사람은 이 학원 학생이다.

## 한 줄 요약

**신청을 제출하면 같은 트랜잭션에서 명부에 들어간다.** 그 명부 행의 반 칸은 비어 있다. 캡틴이 반을 만든 뒤 「크루의 반 지정」으로 채운다.
PRD 가 처음부터 이렇게 적었고, 스펙·코드만 달랐다. **PRD 쪽으로 맞춘다.**

## 왜 — 지금 뭐가 문제인가

1. **문서끼리 말이 달랐다.**
   - [신청 PRD](../../01-planning/stories/crew-submit-application/PRD.md): 「저장 … 같은 트랜잭션에서 명부 편입」
   - [ERD 명부](../erd/STUDY_PARTICIPANT.md): 「신청 제출 시 생기고 … 제출 = 명부 편입」
   - [반 편성 스펙](../../specs/study-group/spec.md): 명단 응답의 `groupId` 가 「반 미배정이면 null」 — 반 없는 명부 행을 이미 가정했다
   - [신청 스펙](../../specs/study-application/spec.md)만 「신청 제출 시 명부를 만들지 않는다」였다. 코드도 이쪽이다
2. **왜 스펙만 달랐나.** 명부 행의 반 칸이 비면 안 되게(`NOT NULL`) 만들어져 있다. 그런데 신청하는 순간에는 넣을 반이 없다. 그래서 「신청 시 분반 배정 제거」 때 명부 편입까지 같이 빠졌다 ([09-30 결정](2026-09-30-application-default-group.md) 「신청할 때는 분반을 배정하지 않는다」).
3. **그 결과 정원이 영영 안 찬다.** 정원 검사는 명부의 `ACTIVE` 인원을 센다. 신청해도 명부에 아무도 안 들어가니 늘 0명이다.
4. **명부를 만드는 코드가 어디에도 없다.** 신청자 탭의 반 지정 · 출석부 · 내 스터디가 읽을 행이 생기지 않는다.

## 정해진 것

| 무엇 | 전 (스펙·코드) | 후 |
|---|---|---|
| 신청 제출 | 신청서만 저장 | 신청서 저장 + **같은 트랜잭션에서 명부 행 insert** — `ACTIVE` · `MEMBER` · 반 비움 |
| 명부 행의 반 (`STUDY_GROUP_ID`) | 꼭 있어야 함 (`NOT NULL`) | **비어 있어도 된다** (NULL = 반 미배정) |
| 반 지정 | 명부에 넣는 시점이 미정 | 「크루의 반 지정」(`PATCH …/participants/{pid}/group`) 이 빈 반을 처음 채우고, 이후 이동도 같은 API |
| 정원 검사 | 명부를 세지만 명부가 비어 있음 | 그대로 명부를 센다 — 이제 맞게 찬다. 마지막 자리 동시 신청을 막으려 모집 회차 행을 잠근다 |

반은 **비워 두는 것**이다. 첫 반에 자동으로 넣지 않는다 — 09-30 결정(「캡틴의 실제 배정과 다른 명부가 만들어진다」)은 그대로다.

## 영향 — 누가 무엇을 해야 하나

**백엔드 (스터디 스쿼드)** — 아직 코드는 안 바뀌었다. 아래가 할 일이다.

1. 마이그레이션: `STUDY_PARTICIPANT.STUDY_GROUP_ID` 를 NULL 허용으로 (다음 번호 `V38`). 엔티티 `StudyParticipant` 의 `nullable = false` 도 푼다
2. `StudyApplicationService.submit` 에서 신청 저장 뒤 명부 행 insert. 정원 검사 전에 모집 회차 행 잠금
3. 반이 빈 행을 읽는 곳 점검 — 반으로 거르는 조회(출석부 · 회차 · 네비게이터 판정)는 빈 반 행을 자연히 건너뛴다. **내 스터디**(`MyStudyQueryService`) · **참여 명단**처럼 사람 기준으로 읽는 곳은 반이 null 이어도 깨지지 않는지 본다
4. `UNIQUE(ACCOUNT_ID, STUDY_GROUP_ID)` 는 NULL 을 여럿 허용한다. 같은 기수 중복 신청은 지금처럼 계정 잠금 + 기존 신청 확인으로 막는다

**프론트**: 백오피스 신청자 탭 명단에서 반이 비어 있는 크루를 「미배정」으로 보여 준다 (스펙상 `groupId` null — 이미 있는 계약).

**디스코드 자동화**: 신청 제출 = 명부 편입이 되므로, 스터디 role 을 **신청 제출 때** 주면 된다 — 자동화 목록 그대로다 ([디스코드 자동화 share](2026-10-18-discord-automation-gap.md) 질문 3).

**기획**: 할 일 없음. PRD 가 이미 이 내용이다.
