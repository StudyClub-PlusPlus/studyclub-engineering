# 문의·파일·감사 기록을 하루 간격으로 정리한다

## 미리 알아야 할 것

감사 기록은 운영자가 누구의 정보를 봤고 어떤 권한을 바꿨는지 남기는 장부다.
이 장부는 계정 탈퇴 사유를 세는 통계와 목적이 다르다.
파일 삭제는 저장소 장애로 실패할 수 있어 재시도 표시가 필요하다.

## 정해진 것

서류함마다 보관 기한은 다르게 붙이되, 매일 정리하는 담당 창구는 한곳에 둔다.
문의·파일·감사 기록의 실행 설정과 결과를 함께 관리한다.
각 삭제 규칙과 실패 처리는 별도로 유지한다. 한 작업이 실패해도 다른 작업은 진행한다.
알림 발송은 기존처럼 30초 간격을 유지한다.

| 기록 | 보관 기간 |
|---|---|
| 답변한 문의 | 첫 답변일부터 1년 |
| 미답변 문의 | 접수일부터 1년 |
| 이메일·디스코드 조회, 일반 크루 참여 중단 | 행위일부터 1년* |
| 캡틴·네비게이터 역할 변경, 권한 말소 | 행위일부터 3년 |
| 네비게이터 참여 중단 | 권한 말소를 포함하므로 3년 |

\* 접속기록 2년 보관 의무에 해당하면 2년으로 설정한다. 운영 적용 전에 실제 회원 규모와 수집 항목을 확인해야 한다. 일반 참여 중단에만 특별히 1년을 정한 법 조항이 있는 것은 아니다. 법령과 상세 기준은 [스펙](../../specs/data-retention/spec.md)에 둔다.

- 같은 감사 기록 표에 접속 IP와 당시 역할을 추가한다. 계정이 없어져도 ID·IP를 완전한 익명 정보로 보지 않는다.
- 캡틴·활동 중인 네비게이터가 탈퇴하면 권한 말소 기록을 남긴다. 기록 저장에 실패하면 탈퇴 데이터 변경도 취소한다.
- 과거 참여 중단에 당시 역할이 없으면 추정해서 삭제하지 않는다. 보류 건수를 확인하고 근거가 있을 때 분류한다.
- 정리는 서버 시작 1분 뒤부터 시작하고 실행 완료 후 하루 간격으로 반복한다. 자정 고정 실행은 아니다.
- 한 번에 최대 100개씩 읽는다. 파일 삭제 실패는 다음 정리에서 재시도한다. 계정 탈퇴 직후 파일 삭제는 그대로 유지한다.
- 정리 결과는 기존 서버 로그와 관측 지표로 확인한다. 정리 실행 이력용 데이터베이스 표를 추가하지 않는다.

## 영향 — 누가 무엇을 해야 하나

- 개발자는 V53·V55 마이그레이션과 서버 변경을 함께 검토한다. 스테이지는 기존 방식대로 스키마를 반영하며 실제 적용 절차를 별도로 확인한다.
- 운영자는 적용 전 2년 보관 의무 여부와 신뢰할 프록시 범위를 확인한다. 프록시는 실제 요청자와 서버 사이에서 요청을 중계하는 서버다. 아무 전달 헤더나 믿으면 사용자가 가짜 IP를 기록할 수 있다.
- 운영자는 정리 실패·48시간 이상 성공 기록 없음·과거 역할 미상 보류 건수를 관측한다. 실제 알림 연결은 별도 배포 작업이다.
- 기획 담당자는 출시 전 개인정보처리방침에 보관 기간과 접속 IP 수집을 반영한다. 신청서 통계화·분석 서비스 기록 삭제·문의 이미지 비공개 전환은 이번 범위에 포함하지 않는다.

## 2026-11-01 보완: 각 기록에 적용 규칙과 만료일을 저장한다

- 문의·감사 로그에 적용한 보관 규칙(종류 + V1)과 만료일을 추가한다. 기존 생성일·첫 답변일은 그대로 활용한다. 약관 동의 버전 1.0은 바꾸지 않는다.
- 현재 데이터는 모두 테스트 기록이고 V1이다. 초기화하지 않은 기록만 원래 날짜로 만료일을 채운다. 배포일로부터 새로 1년/3년을 세지 않는다. 당시 역할을 모르는 참여 중단 기록은 기존처럼 삭제를 보류한다.
- 서버가 시작할 때와 일일 정리 전에 최대 100건씩 초기화한다. 스테이지와 Flyway 환경 모두 동일한 데이터 초기화 코드를 사용한다. 여러 번 실행해도 이미 저장한 규칙·만료일은 바뀌지 않는다.
- 삭제할 때는 저장된 만료일만 확인한다. 첫 답변은 이미 정한 규칙에 따라 만료일을 갱신하고, 답변 수정은 연장하지 않는다.
- 앞으로 새 보관 규칙을 도입하더라도 과거 기록을 일괄 변경하지 않는다. 기존 V1 정의를 고치지 않고 새 버전으로 추가하며, 과거 기록 변경이 필요하면 근거·대상·적용일을 따로 검토한다. 현재의 1년/2년 설정도 새 기록에만 적용한다.
