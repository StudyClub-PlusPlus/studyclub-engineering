# 10-24 리드 · 디스코드 스쿼드 회의 — 권한은 백엔드가 보고 봇은 시킨 일만 한다, 캡틴은 디스코드 연동이 필수

## 미리 알아야 할 것

- **디스코드 봇**(`discord/` 폴더): 우리 디스코드 서버(= **길드**)에서 채널을 만들고 role 을 붙였다 떼는 프로그램이다. 백엔드가 불러야 일한다.
- **role**: 디스코드에서 사람에게 붙이는 이름표. 길드에는 **captain role** 과 **navigator role** 이 하나씩 있다. 스터디마다 스터디 role 도 하나 있다.
- **캡틴**: 운영진(웹의 `ADMIN`). **네비게이터**는 반을 이끄는 참여자(웹의 `LEADER`), **크루**는 일반 참여자(`MEMBER`)다. 캡틴과 네비게이터는 다른 역할이다.
- **디스코드 연동**: 웹 계정에 디스코드 계정 번호(디스코드 ID)를 붙이는 일이다 (`ACCOUNT.DISCORD_ID`).
- **SSOT**(Single Source of Truth, 하나뿐인 진짜 원본): 같은 정보가 여러 곳에 있을 때 **어느 쪽을 믿을지** 정한 그 한 곳이다.
- **권한 확인**: 「이 사람이 이 일을 해도 되나」를 따지는 일이다. 지금은 웹 백엔드와 봇이 **둘 다** 따진다.
- **`X-Discord-User-ID`**: 백엔드가 봇을 부를 때 「누가 시켰나」를 적는 칸이다. 사람이 시킨 게 아니면 봇 자신의 번호(`DISCORD_BOT_ID`)를 넣는다 — 이 번호를 앞으로 **시스템 아이디**라 부른다.
- **sync(동기화)**: 웹 명단과 디스코드 role 이 같은 사람을 가리키게 맞추는 일이다.

비유: 백엔드는 **인사팀**, 봇은 **출입증 발급 창구**다. 지금은 창구 직원도 「이 사람 출입증 줘도 되나」를 다시 따진다. 그러다 보니 인사팀이 시켜도 창구가 거절하는 일이 생긴다(질문 5). 앞으로는 **인사팀만 따지고, 창구는 시킨 대로 발급**한다. 대신 누가 창구에서 몰래 출입증을 바꾸면 창구가 인사팀에 알려 준다.

## 한 줄 요약

권한 확인은 **백엔드 한 곳**에서 한다. 봇은 권한 체크를 지우고 시킨 동작만 한다 — 그래서 질문 5(DSC-06)가 풀렸다. **캡틴은 디스코드 연동이 필수**이고, 연동한 사람만 캡틴이 될 수 있다. 새로 생긴 일은 셋이다: 봇 호출 **기록**, 디스코드에서 바뀐 captain · navigator role 을 **웹에 알리기**, 하루 한 번 **전체 명단 보내기**.

## 정해진 것

| # | 결정 | 지금 코드 | 할 일 |
|---|---|---|---|
| 1 | **캡틴은 디스코드 연동이 필수다.** 연동을 마친 사람만 캡틴 권한을 받을 수 있다 | 권한 변경 API(`PATCH /api/admin/users/{accountId}/system-role`)가 연동을 보지 않는다 | **STD-05** — 캡틴으로 올릴 때 미연동이면 거절. 백오피스 회원 목록의 배지 잠금 이유에도 같은 값 |
| 2 | **크루 · 네비게이터는 스터디 신청할 때 연동한다** | 이미 그렇다 — 미연동이면 신청 403 (#298). 화면은 `discordLinked` 로 연동 창을 먼저 띄운다 (#327) | 없음 |
| 3 | **권한 확인은 백엔드에서 한다 (SSOT). 디스코드 API 는 동작만 한다** | 백엔드는 봇을 부르기 전에 명부를 다시 본다 (`StudyRoleSyncListener`). 봇은 navigator role 창구 두 개를 captain 만 받는다 | **DSC-13** — 봇 API 권한 체크를 지운다. 이걸로 **DSC-06(질문 5)이 풀린다** |
| 4 | **권한 확인 시점** — 캡틴은 백오피스에 들어올 때, 캡틴 · 네비게이터는 디스코드 API 를 부르기 전 | 백오피스 API 마다 DB 의 `SYSTEM_ROLE` 을 본다 (`AdminGuardInterceptor`) — 들어올 때보다 더 자주 본다. 봇 호출 전 확인도 이미 한다 | 새로 부르는 곳(DSC-08 등)도 같은 규칙을 따른다 |
| 5 | **`X-Discord-User-ID` 는 그대로 실행한 사람으로 채운다.** 사람이 실행한 게 아니면 시스템 아이디. 봇은 이 값으로 권한을 따지지 않지만, **디스코드 채널에 메시지를 남길 때 보낸 사람**으로 쓴다 | 이미 그렇다 — 스터디 생성은 그 캡틴의 디스코드 ID, 자동 role 은 시스템 아이디 | 없음. 용어만 「시스템 호출」 → 「시스템 아이디」로 맞춘다 (DSC-13) |
| 6 | 🆕 **디스코드 API 호출을 기록한다.** 스터디 스쿼드: 스터디 생성(채널 · role 만들기), navigator role 부여 · 회수. 커뮤니티 스쿼드: 디스코드 알림 발송 | 실패할 때만 서버 로그(WARN)가 남는다. 성공은 남지 않는다 | **STD-06** · **COM-04** — 형태는 [물어볼 것 2](#물어볼-것) |
| 7 | 🆕 **디스코드에서 role 이 바뀌면 웹에도 알린다.** captain · navigator 인원이 바뀔 때만 보낸다 (권한 확인이 필요한 건 이 둘뿐이라서) | 웹 → 디스코드 한 방향뿐이다 | **DSC-14** (봇이 보낸다) · **DSC-16** (백엔드가 받는다) |
| 8 | 🆕 **하루 한 번 captain · navigator 전체 명단을 웹에 보낸다.** 무슨 일로 어긋나도 다음 날이면 맞는다 — **하루 정도 늦는 건 감수한다.** 봇에 이미 하루 한 번 도는 모니터링 작업에 얹는다 | 없음 | **DSC-15** (봇) · **DSC-16** (백엔드) |

### 질문 5 · 6 이 어떻게 정리됐나 ([디스코드 자동화](2026-10-18-discord-automation-gap.md#물어볼-것))

- **질문 5 — 결정됨.** 봇이 권한 체크를 지우므로 navigator role 창구도 시스템 아이디로 부를 수 있다. 네비게이터 · 담당 캡틴이 참여를 중단시켜도 백엔드가 navigator role 을 회수할 수 있다.
- **질문 4 — 사라졌다.** 캡틴의 디스코드 ID 없이도 백엔드가 시스템 아이디로 부른다. 게다가 캡틴은 연동이 필수가 됐다.
- **질문 6 — 남은 것은 백엔드 몫이다.** 「다른 진행 중 스터디에서 활성 네비게이터면 navigator role 을 떼지 않는다」는 **권한 판정**이다. 결정 3 대로 백엔드가 따지고, 봇은 떼라면 뗀다. 페이로드(`previousRole` · `newRole`)는 #303 그대로 — 디스코드 스쿼드는 리뷰만 하면 된다.

## 물어볼 것

1. **디스코드에서 바뀐 role 을 받으면 웹은 무엇을 하나?** (기획 · 디스코드 스쿼드) — 가장 중요하다
   - 웹이 SSOT 라서, 받은 값을 그대로 웹에 덮어쓰면 안 된다. 그러면 디스코드에서 role 만 붙여도 캡틴이 된다.
   - 고르는 길:
     - **(가) 웹 기준으로 디스코드를 되돌린다** — 웹에서 캡틴이 아니면 captain role 을 떼고, 웹에서 네비게이터면 navigator role 을 다시 붙인다
     - (나) 기록 · 알림만 — 운영 채널이나 백오피스에 「어긋남」을 띄우고 사람이 고친다
     - (다) 백엔드가 확인한 뒤 웹을 바꾼다 — 무엇을 확인하면 바꾸는지 규칙이 필요하다
   - **제안: (가).** 「권한은 백엔드가 본다」와 가장 잘 맞는다. 처음에는 (나)로 기록만 하다가 (가)로 넘어가도 된다.
   - 「여기만 권한 확인이 필요하므로」가 (가) · (다) 중 어느 뜻인지 확인이 필요하다.
2. **호출 기록은 어디에 남기나?** (기획 · 두 스쿼드)
   - 서버 로그(지금 쓰는 로그 · Grafana)에 정해진 모양으로 남긴다 → 작다. 코드만 고친다
   - DB 표에 남기고 백오피스에서 본다 → 표(마이그레이션) · 조회 API · 화면이 생긴다
   - 남길 칸 제안: 언제 · 무슨 동작 · 누가 시켰나(`X-Discord-User-ID`) · 대상 스터디 · 대상 사람 · 결과(성공 · 실패 이유)
3. **지금 캡틴인데 디스코드 미연동인 사람은?** (기획)
   - 결정 1 은 「앞으로 올릴 때」만 막는다. 이미 캡틴인 사람은 그대로다.
   - 이 사람들은 스터디를 만들어도 디스코드 채널이 생기지 않는다 (스터디 생성이 캡틴의 디스코드 ID 로 봇을 부른다).
   - **제안: 백오피스에 들어올 때 연동을 요구한다** — 결정 4 의 「캡틴은 백오피스 입장 시 확인」과 같은 자리다.
4. **웹에서 캡틴으로 올리면 디스코드 captain role 도 붙이나?** (디스코드 스쿼드)
   - 결정 7 · 8 은 디스코드 → 웹 방향이다. 반대 방향(웹 → 디스코드 captain role)을 부르는 창구는 봇에 없다.
   - 없으면 캡틴을 올린 뒤 디스코드에서 손으로 role 을 붙여야 한다 — 그러면 결정 7 로 다시 웹에 알림이 온다.
5. **받는 창구의 모양 · 담당** (디스코드 스쿼드 · 스터디 스쿼드)
   - 백엔드에 봇 → 백엔드 창구가 새로 생긴다. 출석 창구(`POST /api/discord/studies/{discordStudyId}/attendances`)처럼 API 키로 인증한다.
   - 정할 것: 바뀐 한 건(누가 · 어떤 role · 붙음/떨어짐 · 언제)과 하루 한 번 전체 명단의 요청 모양. 같은 알림이 두 번 와도 안전해야 한다.
   - 담당: 백엔드 창구는 스터디 스쿼드가 만드는 걸 제안한다 (명부 · 권한 판정이 여기 있다).

## 영향 — 누가 무엇을 해야 하나

- **디스코드 스쿼드**
  - DSC-13: 봇 API 권한 체크를 지우고, 「시스템 호출」 용어를 「시스템 아이디」로 바꾼다. `X-Discord-User-ID` 는 메시지 보낸 사람 용도로만 읽는다. 이걸로 DSC-06 도 끝난다
  - DSC-14 · DSC-15: captain · navigator role 이 바뀌면 웹에 알리고, 하루 한 번 전체 명단을 보낸다 — 물어볼 것 5 의 모양을 스터디 스쿼드와 먼저 정한다
  - 물어볼 것 4(웹 → captain role)에 답한다
- **스터디 스쿼드**
  - STD-05: 연동한 사람만 캡틴으로 올린다 (admin-users 스펙 · 백오피스 회원 목록 배지)
  - DSC-08 · DSC-09 navigator role 부분: DSC-13 뒤에 시스템 아이디로 부른다. 회수 조건은 백엔드가 따진다
  - STD-06: 스터디 생성 · navigator role 부여 · 회수 기록 (물어볼 것 2 뒤)
  - DSC-16: 디스코드 → 웹 받는 창구 (물어볼 것 1 · 5 뒤)
- **커뮤니티 스쿼드**: COM-04 — 알림 발송 기록. 같은 봇 호출 부품(`DiscordBotClient`)을 쓰니 STD-06 과 한 번에 만드는 게 좋다
