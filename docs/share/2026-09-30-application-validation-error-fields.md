# 신청 검증 오류에 필드별 사유를 별도 객체로 줄 것인가

## 미리 알아야 할 것

공통 오류 응답은 지금 `{errorCode, errorMessage}` 두 칸이다. 신청 API 스펙은 여기에 `fields`라는 필드별 오류 지도를 추가하라고 적혀 있다.

## 한 줄 요약

기존 공통 계약 `{errorCode, errorMessage}`를 유지한다. 별도 `fields` 객체를 추가하지 않고 `errorMessage`에 `answers.reason: empty`처럼 담는다. 신청 스펙도 이 계약에 맞춘다.

## 왜 — 지금 뭐가 문제인가

택배 상자 겉면에 문제를 한 줄로 쓸지, 상자 안에 항목별 체크리스트를 넣을지 정하지 않은 것과 같다. 신청 API 하나만 응답 모양을 바꾸면 프론트의 공통 오류 처리가 갈라진다.

## 결정

- 공통 `ErrorResponse`를 확장하지 않는다.
- 신청 스펙에서 `fields` 요구를 제거한다.

## 영향 — 누가 무엇을 해야 하나

백엔드·프론트엔드는 기존 공통 오류 응답을 사용한다. 답변과 별명 원문은 오류 응답에 넣지 않는다.
