# 로그인 쿠키는 앱(사이트·백오피스)과 환경(stage·운영)마다 따로 읽는다

## 미리 알아야 할 것

| 단어 | 뜻 |
|---|---|
| **로그인 쿠키** | 로그인하면 브라우저에 심는 출입증. `sc_access_token`(사이트) · `bo_access_token`(백오피스) |
| **상위 도메인** | `.studyclub.life`. 화면이 API 를 직접 부르므로 쿠키를 여기에 심는다 — stage·운영·사이트·백오피스·API 가 전부 이 아래다 |
| **Origin** | 브라우저가 요청에 붙이는 "어느 화면에서 왔나" 표시 |

## 한 줄 요약

**한 브라우저에 출입증이 여러 장 있어도, API 는 요청이 온 화면에 맞는 것 하나만 본다.** stage 출입증은 이름부터 다르다.

## 왜 — 뒤집힌 전제

| 이럴 줄 알았다 | 실제 |
|---|---|
| 사이트·백오피스는 쿠키 이름이 달라(`sc_` · `bo_`) 섞이지 않는다 | 같은 상위 도메인이라 브라우저가 **둘 다** 보낸다. API 는 먼저 온 것을 썼다 |
| stage 와 운영은 주소가 달라 따로 논다 | 쿠키 이름·도메인이 같아 **서로 덮어쓴다** |

2026-10-16 stage 에서 사이트로 프로필 사진을 올렸더니 백오피스에 로그인한 **다른 계정**으로 판단돼 403 이 났다.
백오피스 스터디 목록이 통째로 안 뜬 것도 같은 원인이다(사이트 계정으로 판단 → 권한 없음).

## 정한 것

| 무엇 | 어떻게 |
|---|---|
| 앱 구분 | API 가 `Origin` 을 본다. 백오피스 주소(`BACK_OFFICE_ORIGINS`)에서 온 요청은 `bo_` 만, 그 밖의 브라우저 요청은 `sc_` 만 |
| 환경 구분 | `AUTH_COOKIE_ENV=stage` 이면 이름에 넣는다 — `sc_stage_access_token`. **운영은 넣지 않는다** (기존 이름 그대로 — 운영 사용자가 로그아웃되지 않게) |
| 서버에서 부를 때 | 쿠키를 통째로 넘기지 않고 자기 앱 토큰만 `Authorization` 으로 (백오피스 SSR 도 사이트 bff 와 같게) |

## 영향

- **stage 는 이 변경이 배포되면 로그인이 한 번 풀린다** — 쿠키 이름이 바뀌어서. 다시 로그인하면 된다
- 운영은 영향 없음. 단 운영 API 에 이 코드가 나가기 **전에** `BACK_OFFICE_ORIGINS` 가 들어가 있어야 한다 — 2026-10-16 이미 넣었다
- 로컬은 그대로. 백오피스 기본 주소는 `http://localhost:4701`
