# 문의 첨부 사진은 비공개 폴더에 두고, 작성자와 캡틴만 서버를 거쳐 본다

## 미리 알아야 할 것

- **문의**: 크루가 캡틴에게 보내는 문의·오류 신고. 사진을 최대 3장 붙일 수 있다. 코드 이름은 `feedback`이다.
- **CloudFront**: 사진을 빠르게 나눠 주는 배달 창구(CDN). 우리는 `gigs/` 폴더의 파일만 이 창구로 누구에게나 열어 둔다.
- **공개 주소**: 로그인 없이, 주소만 알면 열리는 사진 주소.
- **비유**: 지금까지는 사진을 **현관 밖 우편함**에 두고 "주소만 알면 가져가세요"라고 한 셈이다. 이제는 **금고에 두고, 신분증을 확인한 직원이 꺼내 보여 준다.**

## 한 줄 요약

문의 첨부 사진은 이제 주소만으로 열리지 않는다. 로그인한 **작성자 본인**과 **현재 캡틴**만, 서버가 요청할 때마다 확인한 뒤 볼 수 있다.

## 왜 — 지금 뭐가 문제였나

오류 신고 스크린샷에는 이메일·닉네임 같은 개인정보가 찍히기 쉽다. 그런데 사진 주소가 서명도 만료도 없는 공개 주소여서, 주소가 한 번 새면 누구나 계속 볼 수 있었다. Slack은 파일 주소(`url_private`)에 인증 토큰이 있어야 열리게 해 둔다. 같은 원칙을 적용했다.

## 정해진 것

- 새 사진은 `private/feedbacks/` 에 올라간다. CloudFront가 열지 않는 폴더라 주소로는 안 열린다.
- 사진은 `GET /api/me/feedbacks/{id}/images/{imageId}`(작성자), `GET /api/admin/feedbacks/{id}/images/{imageId}`(캡틴)로만 본다. 서버가 로그인·권한·보유 기간·삭제 중 여부를 확인하고, 하나라도 어긋나면 404다.
- **서버가 직접 전달하는 방식**을 택했다. 시간 제한이 있는 서명 주소(CloudFront·S3)는 만료 전까지 주소만 있으면 열려서, 캡틴 권한을 잃은 직후에도 볼 수 있다. 서버 방식은 캡틴 권한이나 보유 기간이 바뀌면 바로 막힌다. 대가는 사진을 볼 때마다 서버를 한 번 거친다는 점이다(작성자와 캡틴만 보고, 한 건에 최대 3장이라 부담이 작다).
- 인프라(AWS) 변경은 없다. `gigs/` 밖은 이미 비공개이고, 서버 키에 읽기 권한이 있다.
- **이미 올라간 옛 사진은 옮기지 않기로 했다.** 화면에는 계속 보이지만, 예전에 나간 CloudFront 주소로도 계속 열린다(최대 하루 캐시). 당시 기록은 모두 개인정보가 없는 테스트 자료이고 1년 뒤 자동 삭제된다(PR 리뷰 결정, 2026-11-25).
- **prod 배포 중 일시적인 오류는 감수한다.** 컬럼 삭제 때문에 옛 인스턴스가 잠깐 실패할 수 있지만, 아직 개발자만 쓰는 단계다(PR 리뷰 결정, 2026-11-25).

## 영향 — 누가 무엇을 해야 하나

- **인프라 담당**: stage DB에 `V64__drop_feedback_image_url.sql`(`FEEDBACK_IMAGE.IMAGE_URL` 컬럼 삭제)을 **손으로 한 번** 적용한다. stage는 Flyway가 꺼져 있고, 컬럼이 남으면 새 문의 저장이 실패한다. prod는 Flyway가 적용한다.
- **프론트 개발자**: 문의 사진 `<img>`는 `crossorigin='use-credentials'`로 연다. 응답의 `images[].url`은 공개 주소가 아니라 API 경로다. 이미지가 실패하면 인증을 한 번 갱신하고 다시 요청한다(`RetryableImage`).
- **다른 기능에 개인정보 사진이 필요할 때**: [`docs/flows/image-upload.md`](../flows/image-upload.md)의 「비공개 용도」를 따른다.
