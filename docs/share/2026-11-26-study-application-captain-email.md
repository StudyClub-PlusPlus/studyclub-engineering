# 스터디 신청을 담당 캡틴에게 메일로 알린다

## 미리 알아야 할 것

스터디마다 담당 캡틴이 한 명 있다. 기존 신청 접수는 명부에 신청자를 넣고 운영 디스코드에 알린다. 이번에는 담당 캡틴의 이메일에도 새 신청을 알린다.

## 결정

신청을 접수하면 담당 캡틴의 메일 발송함에 안내 한 장을 넣는다. 실제 우편 배달은 뒤에서 한다는 방식이다. 그래서 메일 발송을 기다리지 않고 신청을 마칠 수 있다.

- 수신자는 신청 시점의 담당 캡틴이다. 스터디를 처음 만든 사람이나 모든 운영진에게 보내지 않는다.
- 담당 캡틴 본인의 신청은 제외한다.
- 메일에는 스터디명과 **신청자 확인하기** 버튼만 둔다. 신청자 이름·이메일·답변은 넣지 않는다.
- 버튼은 백오피스 해당 스터디의 신청자 탭으로 간다. 로그인이 필요하면 기존 로그인 후 돌아온다.
- 담당 캡틴이 없거나 탈퇴했거나 권한이 없으면 신청만 받는다. 메일 양식이 없어도 같다. 누락 사유와 신청 번호는 서버 로그에 남긴다.
- 운영 경고는 기존 디스코드 WARN 채널로 보낸다. 같은 스터디·사유의 첫 건은 바로 알린다. 반복되면 서버별로 10분 동안 모은 누락 건수를 알린다. 개별 로그는 모든 누락을 남기고, 메모리 집계는 서버 재시작 시 사라질 수 있다.
- 설정을 고쳐도 과거 누락을 자동으로 보내지 않는다. 예약하지 않은 건은 발송 이력에 없으며 재발송할 수 없다.
- 발송에 실패한 건은 기존 발송 이력에 남는다. 재발송 시 담당자가 바뀌었다면 이전 담당자에게 다시 보내지 않는다.
- 예약을 DB에 저장하지 못하면 신청도 함께 취소된다. 실제 메일 전송 오류는 이미 완료된 신청을 취소하지 않는다.

## 배포하는 사람이 할 일

1. 기존 로그인용 `BACK_OFFICE_ORIGINS`가 하나의 주소면 메일에도 그대로 쓴다. 여러 주소를 허용하면 메일 대표 주소만 `NOTIFICATION_BACK_OFFICE_BASE_URL`로 지정한다. stage는 `https://back-office-stage.studyclub.life`, 운영은 `https://back-office.studyclub.life`다. 잘못되거나 모호한 주소로는 서버를 시작하지 않는다.
2. 운영은 Flyway V68로 새 양식 한 건을 등록한다. 기존에 같은 조건이 있으면 덮어쓰거나 중복 등록하지 않는다.
3. stage는 Flyway를 쓰지 않으므로 배포 후 백오피스에서 **스터디 신청 알림** 조건으로 시안의 제목·HTML을 한 번 등록하거나 V68을 수동 적용한다. 이번 작업에서 실제 DB는 변경하지 않았다.
4. 기존 `OPS_WARN_WEBHOOK_URL` 이 설정돼 있는지 확인한다. 비어 있으면 개별 서버 로그만 남는다.
5. 아래 테스트 케이스로 확인한다. 실제 운영 회원에게 테스트 메일을 보내지 않는다.
