# 회차는 「시작 + 120분」이 지나면 끝난 것으로 본다 — 지금은 한 번 시작한 회차가 영원히 「진행 중」이다

## 미리 알아야 할 것

| 단어 | 뜻 |
|---|---|
| **회차** (`STUDY_MEETING`) | 반이 한 번 모이는 일. 「3주차 논문 읽기」 같은 한 칸. 출석은 회차마다 찍는다 |
| **예정 시각** (`SCHEDULED_AT`) | 네비게이터가 화면에서 잡은 모임 시각 |
| **실제 시작** (`START_AT`) | 그 회차가 실제로 열린 시각. 지금은 디스코드 `!출석체크` 가 처음 쳐질 때 서버가 찍는다 |
| **실제 종료** (`END_AT`) | 그 회차가 실제로 끝난 시각. **칸은 있지만 아무도 쓰지 않는다** — 이 문서의 주제 |
| **`!출석체크`** | 네비게이터(반장)가 공부방 음성 채널 채팅에 치는 봇 명령. 그 순간 방에 있는 사람을 출석으로 찍는다 |
| **진행 중 판정** | 서버가 「이 회차는 지금 진행 중인가」를 계산하는 규칙. 상태를 저장하지 않고 시각으로 계산한다 |
| **±2시간 창** | `!출석체크` 가 아직 안 열린 회차를 열어 줄 수 있는 범위. 예정 시각 앞뒤 2시간 |

## 한 줄 요약

`END_AT` 을 쓰는 코드가 없어서 **한 번 시작한 회차는 끝나지 않는다.**
그래서 다음 주 `!출석체크` 가 **지난주 회차에 출석을 찍는다.**
**종료를 사람이 누르거나 서버가 저장하지 않고, 시각으로 계산하자**고 제안한다 — `실제 시작(없으면 예정 시각) + 120분` 이 지나면 끝난 회차다.

## 비유 — 퇴근 도장을 아무도 안 찍는 출입 기록

출근 도장은 찍는데 퇴근 도장 기계가 없는 회사를 떠올리면 된다.
기록상 모두가 첫 출근한 날부터 지금까지 계속 「근무 중」이다.
다음 날 출근 도장을 찍으려 하면 기계가 「이미 근무 중이네요」 하고 **어제 기록에 도장을 덧찍는다.**

## 왜 — 지금 뭐가 문제인가

### 1. 종료를 기록하는 곳이 없다

| 시각 | 누가 · 언제 · 어떻게 | 코드 |
|---|---|---|
| 시작 `START_AT` | `!출석체크` 를 처음 칠 때 서버가 자동으로 | `StudyMeeting.start()` · `DiscordAttendanceService.pickMeeting()` |
| 종료 `END_AT` | **없다.** 회차를 만들 때 비우고(`schedule()` · `kickoff()`), 채우는 메서드·봇 명령·화면 버튼이 없다 | — |

ERD(`docs/erd/STUDY_MEETING.md`)는 `DONE = END_AT IS NOT NULL` 을 「끝난 회차」로 정의해 두었다. 하지만 누가 언제 그 값을 쓰는지는 정하지 않았다.

### 2. 그래서 다음 회차 출석이 지난 회차로 간다 (코드로 추적한 결과)

`!출석체크` 가 회차를 고르는 순서는 이렇다 (`DiscordAttendanceService.java:197-232`).

1. **진행 중인 회차** — `START_AT 있음 AND END_AT 없음`. **시간 제한이 없다**
2. 없으면 예정 시각 ±2시간 안의, 아직 안 열린 회차를 연다

`END_AT` 이 영영 비어 있으니 1번이 항상 먼저 걸린다.

| 날짜 | 네비게이터가 한 일 | 서버가 고른 회차 | 결과 |
|---|---|---|---|
| 11/3 | 1회차 시간에 `!출석체크` | 진행 중 없음 → 1회차를 연다 | ✅ 1회차에 출석 |
| 11/10 | 2회차 시간에 `!출석체크` | **1회차가 아직 진행 중** | ❌ 1회차에 다시 찍힘 · 2회차는 열리지도 않음 |
| 11/17 | 3회차 시간에 `!출석체크` | 여전히 1회차 | ❌ 같은 문제 |

반이 보이스 채널 둘을 써서 진행 중 회차가 여럿이어도 거절하지 않는다(디스코드 출석 스펙). 그래서 에러도 나지 않고 **조용히 틀린 회차에 쌓인다.**
단위 테스트가 이 경우를 잡지 못한 것은, 테스트 픽스처가 생성자로 `endAt` 을 직접 넣을 수 있기 때문으로 보인다. 운영 경로에는 그 길이 없다.

### 3. 화면은 이미 「예정 + 120분」으로 종료를 추정하고 있다

사용자 사이트 「내 스터디」는 `endAt` 이 비면 `scheduledAt + 120분` 을 종료로 본다.
- `frontend/apps/core-front/src/lib/joined.ts:91-99` `meetingEnd()`
- `specs/my-studies/spec.md` 「화면이 응답에서 계산하는 것」

**서버와 화면이 「끝났다」를 서로 다르게 판정하고 있다.** 화면은 2시간 뒤 끝났다고 보는데, 서버는 영원히 진행 중이라고 본다.

## 고를 수 있는 방식

| | 방식 | 좋은 점 | 문제 |
|---|---|---|---|
| **A** | 네비게이터가 `!종료` 명령을 친다 → `END_AT` 기록 | 실제 종료 시각이 정확하다 | **빼먹으면 지금 버그가 그대로 남는다.** 디스코드 출석 스펙이 `!시작` 을 없앤 이유가 바로 「빼먹는 실수가 더 흔하다」였다 |
| **B** ⭐ | **저장하지 않고 시각으로 계산** — `시작 기준 + 120분` 이 지나면 끝난 회차 | 사람이 할 일이 없다. 「상태는 저장하지 않고 시각으로 계산한다」는 ERD 원칙과 같다. 화면이 이미 쓰는 120분과 맞는다 | 120분보다 긴 모임은 끝나기 전에 「끝남」이 된다 (아래 질문 2) |
| C | 서버 스케줄러가 주기적으로 `END_AT` 을 써 넣는다 | 기록이 DB 에 남는다 | 판정 근거가 결국 B 와 같은 시각 계산이다. 저장만 하나 늘고, 서버를 여러 대 띄우면 중복 실행을 막아야 한다 |
| D | 다음 회차를 열 때 앞 회차를 닫는다 | 구현이 짧다 | 다음 회차가 없으면(마지막 회차) 영원히 안 닫힌다. 화면 판정에는 쓸 수 없다 |
| E | 음성 채널이 비면 닫는다 | 실제와 가깝다 | 공부방 하나를 여러 반이 같이 쓴다(디스코드 출석 스펙). 채널로는 어느 반 회차인지 가를 수 없다 |

**B 를 제안한다.** A 는 나중에 B 위에 얹을 수 있다. `!종료` 가 생기면 `END_AT` 이 계산값보다 우선하면 된다.

## 물어볼 것

1. **B(시각 계산)로 가도 되나?** — 추천: 예
2. **회차 길이를 몇 분으로 보나?** — 추천: **120분**. 화면(`MEETING_MIN`)과 my-studies 스펙이 이미 쓰는 값이라 새로 정하는 숫자가 아니다.
   - 120분이 넘는 모임에서 2시간 뒤 `!출석체크` 를 치면 `noMeeting`(지금 모이는 회차 없음)이 된다. 그때는 네비게이터가 백오피스 출석부에서 손으로 고친다 — 「끝난 회차에 소급 입력하지 않는다」는 지금 규칙과 같다.
   - 실제로 2시간 넘게 모이는 반이 있는지 스터디팀이 알려 주면 값을 바꾼다. 근거가 없어 지금은 120을 그대로 둔다.
3. **화면도 서버 판정을 받아 쓰게 하나?** — 추천: 예. 서버가 회차마다 `endsAt`(종료 기준 시각)을 내려 주고, 화면은 `meetingEnd()` 계산을 지운다. 「판정은 서버가 내려준다」([10-09 결정](2026-10-09-server-owns-judgments.md)) 대로다. 이번 버그 수정에 꼭 필요하지는 않아 따로 해도 된다.

## 스펙 초안 — B 로 정해지면 이렇게 고친다

### 종료 기준 시각 (새 정의)

```
종료 기준(endsAt) = END_AT                                  ← 있으면 (지금은 늘 비어 있음, A 를 붙이면 생김)
                 ?? max(SCHEDULED_AT, START_AT) + 회차 길이   ← 없으면 계산. START_AT 이 없으면 SCHEDULED_AT
회차 길이 = 120분 (상수 하나 · StudyMeeting.DURATION)
```

`max` 를 쓰는 이유: 예정보다 **늦게** 열린 회차는 연 시각부터 센다. 예정 시각 2시간 뒤에 열었는데 예정 기준으로 세면 열자마자 끝나 버린다. **일찍** 열린 회차는 예정 시각부터 센다. 화면이 보여 주는 예정 종료와 같다.

### `docs/erd/STUDY_MEETING.md` 「상태」 표

| 판정 | 지금 | 바꾼 뒤 |
|---|---|---|
| `SCHEDULED` | `START_AT IS NULL AND now < SCHEDULED_AT` | 그대로 |
| `IN_PROGRESS` | `START_AT IS NOT NULL AND END_AT IS NULL` | `START_AT IS NOT NULL AND now < endsAt` |
| `DONE` | `END_AT IS NOT NULL` | `START_AT IS NOT NULL AND now ≥ endsAt` |
| `MISSED` | `START_AT IS NULL AND now > SCHEDULED_AT + 여유` (여유 미정) | 여유 = **±2시간 창**(`MEETING_PICK_WINDOW`). `!출석체크` 가 더는 열 수 없는 회차 |

`END_AT` 컬럼 설명: 「실제 종료」 → 「실제 종료 — 종료 명령이 생기면 기록한다. 비면 종료 기준은 시각으로 계산한다」.

### `specs/discord-attendance/spec.md` 「회차 판정 규칙」

```
1) 진행 중인 회차  (START_AT IS NOT NULL AND now < endsAt)      ← END_AT IS NULL 을 바꾼다
   여럿이면 START_AT 이 가장 최근인 것
2) (그대로) SCHEDULED_AT 이 now ± 2h 이내이고 아직 시작 안 한 회차 → 연다
3) (그대로) 둘 다 없으면 noMeeting[]
```

경계 표에 두 줄을 더한다.

| 경계 | 결과 | 근거 |
|---|---|---|
| 지난주 회차가 열린 채로 이번 주 `!출석체크` | 이번 주 회차를 연다 | 지난주 회차는 `endsAt` 이 지났다 |
| 연 지 2시간 10분 뒤 다시 `!출석체크` | `noMeeting[]` | 끝난 회차다. 화면에서 수정 |

「회차 종료 시 미체크 인원을 ABSENT 로」(126줄)는 지운다. 회차를 추가할 때 이미 전원을 `ABSENT` 로 깔아 두므로(2026-10-02) 종료 때 할 일이 없다.
