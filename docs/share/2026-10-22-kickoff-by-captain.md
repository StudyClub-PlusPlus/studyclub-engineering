# 킥오프는 캡틴이 백오피스 일정 탭에서 정한다 — 회차 추가가 자동으로 만들지 않고, 네비게이터는 고치지 않는다

## 미리 알아야 할 것

- **킥오프**: 스터디 반의 첫 모임이다. 여기서 규칙 · 일정 · 발표자를 정한다. 일정 표에는 「0회차」로 맨 위에 보인다. 출석은 찍지만 출석률에는 넣지 않는다.
- **반**(분반): 한 스터디 안에서 모이는 시간이 다른 묶음이다. 회차와 킥오프는 반마다 따로 있다.
- **캡틴**: 운영진(ADMIN)이다. 백오피스에서 스터디와 반을 만든다. **네비게이터**는 반을 이끄는 참여자(LEADER)다. 둘은 다른 역할이다.
- **API**: 화면이 서버에 「이것 해 줘」 하고 부탁하는 창구다. 주소마다 할 수 있는 일이 정해져 있다.

비유: 킥오프는 **개강 오리엔테이션**이다. 오리엔테이션 날짜는 학과 사무실(캡틴)이 정해서 공지한다. 조교(네비게이터)는 그날 정해진 수업 일정을 시간표에 넣을 뿐, 오리엔테이션 날짜를 옮기지 않는다.

## 무엇이 바뀌었나

| 무엇 | 전 (10-14) | 후 (10-22) |
|---|---|---|
| 킥오프가 생기는 때 | 회차 없는 반에 처음 「회차 추가」를 하면 서버가 첫 회차 한 주 전에 함께 만든다 | **캡틴이 백오피스 일정 탭 「킥오프 정하기」로 만든다.** 회차 추가는 킥오프를 만들지 않는다 |
| 킥오프 날짜를 고치는 사람 | 네비게이터 · 캡틴 (사용자 사이트 일정 표) | **캡틴만, 백오피스 일정 탭 「킥오프 수정」으로.** 사용자 사이트에서는 네비게이터도, 스터디를 만든 캡틴도 고치지 않는다 |
| 지난 날짜 | 고칠 수 없었다 | 캡틴은 지난 날로도 정한다 — 이미 운영 중인 반의 킥오프를 나중에 적는다 |
| 출석 행 | 정규 회차처럼 결석(ABSENT)으로 깔았다 | **만들지 않는다.** 기록이 없으면 출석부 킥오프 칸은 빈 칸이다. 디스코드 출석 · 출석부 저장이 행을 만든다 |
| 킥오프가 없는 반 | 생길 수 없었다(회차가 있으면) | 생길 수 있다. 그동안 정규 회차는 순서 규칙 없이 만든다. 킥오프를 정하면 1회차보다 앞이어야 한다 |

## 왜

- **자동으로 생긴 줄이 헷갈렸다.** 네비게이터가 회차 4개를 넣었는데 표에 만들지 않은 「킥오프」 줄이 하나 더 생겼다. 날짜도 고르지 않은 날이었다.
- **킥오프는 캡틴이 정한다.** 실제 운영에서 킥오프 날은 캡틴이 반을 만들며 정해 알린다. 네비게이터는 킥오프에서 정한 일정을 회차로 넣는다.
- **지난 킥오프 문제가 사라진다.** 자동으로 만들면 첫 회차가 일주일 안일 때 킥오프가 이미 지난 날로 생겨 고칠 수 없고, 출석부에는 모두 결석으로 보였다.

## 이렇게 동작한다

- 백오피스 스터디 운영 › 일정 탭 › 반을 고르면 제목 줄에 「킥오프 정하기」(없을 때) 또는 「킥오프 수정」(있을 때) 버튼이 있다.
- 창에서 일자 · 시작 시각(반 시간대)을 고른다. 처음 값은 1회차 한 주 전 · 반의 스터디 시각이다.
- 1회차 날이나 그 뒤면 막는다: 「킥오프는 1회차(10/15(목))보다 앞이어야 합니다.」
- 사용자 사이트 스터디 일정의 킥오프 줄은 글자로만 보인다. 마우스를 올리면 「킥오프 일정은 캡틴이 정합니다.」

## 남은 것

- **back-office-front 일정 탭 서버 연결**: 「킥오프 정하기 · 수정」 화면은 붙였지만 아직 브라우저 저장소에 남는다. 서버 API(회차 목록 · 킥오프 정하기)는 준비됐는데 둘 다 경로에 반 ID 가 필요하고, 백오피스가 반 ID 를 받을 반 목록 API(`GET /api/admin/studies/{studyId}/participants`)가 아직 없다.
- **백오피스 회차 추가 · 수정 · 삭제**: 사이트 API 는 스터디를 만든 캡틴만 통과한다. 다른 캡틴이 백오피스에서 회차를 고치려면 `/api/admin` 쓰기 API 가 필요하다 — 정하지 않았다.
- 운영 중인 반의 킥오프를 한꺼번에 채울지(데이터 백필)는 정하지 않았다. 지금은 캡틴이 반마다 정한다.
