# 데이터 보관 기한과 자동 정리

상태: 구현완료 (브랜치 검증 완료, 미배포) · 결정일: 2026-10-31

## 목적과 범위

문의·파일·운영 감사 기록을 보관 기한에 맞춰 지운다. 실행 설정·실행 결과는 `api.cleanup`에서 관리하고, 삭제 규칙과 트랜잭션은 각 도메인 서비스가 담당한다. 새 API나 운영 화면은 만들지 않는다. 알림 발송의 30초 폴링과 탈퇴·프로필 교체 직후 파일 삭제는 그대로 유지한다.

## 보관 기준

| 대상 | 기준 시점 | 기간 | 파기 범위 |
|---|---|---|---|
| 첫 답변이 있는 문의 | 최초 `REPLIED_AT` | 달력상 1년 | `FEEDBACK`, `FEEDBACK_IMAGE`, 연결된 저장소 파일 |
| 답변이 없는 문의 | `CREATED_AT` | 달력상 1년 | 동일 |
| 연결되지 않은 업로드 | `CREATED_AT` | 기존 24시간 | `STORAGE_OBJECT`와 파일 |
| 이미 삭제 예약한 파일 | 삭제 예약 직후; 실패 시 다음 정리 | 재시도 | 실제 파일 삭제 성공 후 저장소 행 삭제 |
| 이메일·디스코드 조회 | 감사 로그 `CREATED_AT` | 1년* | 해당 `ADMIN_AUDIT_LOG` 행 |
| 일반 크루 참여 중단 | 감사 로그 `CREATED_AT` | 1년* | 해당 감사 로그 행 |
| 캡틴↔크루, 네비게이터↔크루 권한 변경 | 감사 로그 `CREATED_AT` | 3년 | 해당 감사 로그 행 |
| 네비게이터 참여 중단·계정 탈퇴로 인한 권한 말소 | 감사 로그 `CREATED_AT` | 3년 | 해당 감사 로그 행 |

UTC 달력의 `plusYears`로 계산하고 만료 시각 이상이면 지운다. 윤년 2월 29일은 다음 해당 연도의 2월 말일이다. 추가 답변·수정·탈퇴·배포로 시계를 재시작하지 않는다. 문의 파일 삭제 실패 시 `DELETING` 행을 남겨 재시도한다. S3 버전 관리·백업의 실제 영구 파기는 별도 저장소 수명주기 확인 대상이며 앱 삭제 성공만으로 과거 버전까지 삭제됐다고 간주하지 않는다.

\* 접근 기록 1년은 현재 MVP의 운영 기준이다. 「개인정보의 안전성 확보조치 기준」 제8조는 원칙적으로 1년 이상, 5만 명 이상 정보주체 또는 민감정보·고유식별정보 처리 등 해당 경우 2년 이상이다. 운영 적용 전에 실제 규모·수집 항목을 확인하고 해당 시 `audit.retention.access-years=2`로 설정한다. 신청서 자유입력의 존재만으로 해당 여부를 단정하지 않는다. 제5조 제3항은 접근 권한 부여·변경·말소 기록을 최소 3년 보관하도록 한다. 일반 참여 중단에 특별히 1년을 지정한 법 조항은 없으며 개인정보 처리 활동의 추적 기준으로 정했다.

## 감사 로그 저장 계약

기존 `ADMIN_AUDIT_LOG`를 사용한다. 행위와 로그 저장은 같은 트랜잭션이다. 로그 저장이 실패하면 권한 변경·탈퇴도 취소하고 개인정보 조회 응답을 내보내지 않는다. `ACCOUNT_LEAVE_REASON`은 기존처럼 계정 ID 없는 탈퇴 사유 집계로 유지한다.

공통: 행위자·대상 계정 ID, 행위 종류, 변경 전후 값, 생성 시각과 `ACTOR_IP`(IPv4/IPv6, 없으면 null). 참여 관련 신규 기록은 `PARTICIPANT_ID`, `PARTICIPANT_ROLE`(행위 직전 역할)을 함께 저장한다. 탈퇴 권한 말소는 `REASON=ACCOUNT_DELETION`이다. 이메일·디스코드 원문·닉네임·문의/신청서 내용은 복제하지 않는다. ID·IP도 개인정보일 수 있으므로 접근 제한과 만료 파기 대상이다.

| ACTION | 기존/추가 | 의미와 저장 방식 |
|---|---|---|
| `EMAIL_REVEAL`, `DISCORD_REVEAL` | 기존 + IP | 누가 누구의 개인정보를 조회했는지 |
| `ROLE_CHANGE` | 기존 + IP | 계정 역할의 변경 전후 값 |
| `PARTICIPANT_ROLE` | 기존 + IP·역할/참여 ID 스냅샷 | 명부 역할의 변경 전 값과 대상 참여 ID; 기존 BEFORE/AFTER 형식 유지 |
| `WITHDRAW` | 기존 + IP·직전 역할/참여 ID | 일반 크루 1년*, 네비게이터 3년; 중복 말소 로그는 만들지 않음 |
| `ACCOUNT_ROLE_REVOKE` | 추가 | 캡틴 탈퇴: ADMIN → NONE, 본인이 행위자·대상 |
| `PARTICIPANT_REVOKE` | 추가 | ACTIVE/PAUSED 네비게이터 탈퇴: LEADER → NONE, 참여 행마다 1건 |

이미 중단·완료된 참여에는 탈퇴 말소 로그를 추가하지 않는다. 실제 변화가 없는 역할 요청에도 기록을 만들지 않는다. 과거 로그의 IP나 역할을 현재 값에서 추정해 채우지 않는다. **직전 역할이 없는 과거 WITHDRAW는 자동 삭제에서 제외**하고 보류 개수를 관측한다. 신뢰할 수 있는 과거 증거로 분류한 뒤 별도 검토하여 해소한다.

## IP 신뢰 경계

기본은 서버가 직접 관측한 접속 주소다. `audit.trusted-proxies`에 명시한 중계 서버에서 온 요청에만 `X-Forwarded-For`를 사용하며 오른쪽부터 신뢰 중계 서버를 제거한 첫 주소를 선택한다. 일반 사용자가 보낸 임의 헤더는 믿지 않는다. 잘못된 헤더는 직접 관측 주소로 되돌린다. IP 리터럴만 받고 호스트 이름 조회는 하지 않는다. 요청 문맥이 없는 내부 호출과 과거 로그는 null을 허용한다.

배포 전에 실제 프록시 체인과 외부 헤더 덮어쓰기/추가 정책을 확인하고 신뢰 범위를 설정한다. 컨테이너의 자동 forwarded-header 해석과 이 해석을 중복 적용하지 않는다. 넓은 사설망 전체를 근거 없이 신뢰하지 않는다. IP 원문은 일반 애플리케이션 로그·메트릭 태그에 넣지 않는다.

## 실행과 실패 처리

- `cleanup.enabled`로 전체 정리를 제어한다. 기본 시작 지연 60초, **각 실행 완료 후 24시간 간격**이다. 자정 실행이 아니며 재시작 시 시작 지연 뒤 누락분을 검사한다. 만료 즉시 정각 삭제를 보장하지 않고 정상 가동 시 다음 일일 검사에서 삭제한다.
- 문의·저장소·감사 로그는 각각 활성화할 수 있다. `cleanup.fixed-delay-ms`와 `cleanup.initial-delay-ms`로 공통 주기를 관리한다. 전용 스케줄러에서 작업별로 실행하여 알림 발송 스레드를 점유하지 않는다.
- 후보는 ID 순서로 최대 100개씩 읽는다. 전체 삭제를 하나의 트랜잭션으로 묶지 않는다. 한 작업/항목 실패가 다른 항목·작업의 삭제를 막지 않는다.
- 문의는 기존 계정→문의 잠금 및 만료 재확인, 파일은 조건부 삭제 예약과 재시도, 감사 로그는 보존 규칙 확인 후 삭제한다. 여러 서버가 같은 대상을 처리해도 결과가 안전하다.
- 실행 결과는 일반 로그와 기존 Micrometer에 작업명, 시각, 삭제·실패·보류 건수, 소요 시간으로 남긴다. 0건 실행도 기록하며 오류 메시지에 개인정보를 넣지 않는다. 실행 기록 전용 DB 테이블은 추가하지 않는다.
- 운영 모니터링은 최근 성공 시각 경과(예: 48시간), 실패 증가, 과거 WITHDRAW 보류 건수로 확인한다. 메트릭은 프로세스 재시작 시 초기화되므로 기존 Prometheus 수집이 필요하다. 실제 알림 라우팅·배포는 이 구현과 별도다.

## 검증 기준

1. 1년/3년 경계 및 윤년, 미답변·최초 답변 기준, 과거 역할 미상 보류.
2. 이메일·디스코드·역할 변경·참여 중단 요청의 IP 및 위조 헤더 차단.
3. 캡틴/네비게이터 탈퇴 기록과 로그 실패 시 탈퇴 롤백, 재요청 중복 방지.
4. 100건을 넘는 만료 데이터 처리, 파일 실패 후 재시도, 다른 정리 작업의 독립 실행.
5. 정리 비활성화·일일 기본값·전용 실행기와 기존 알림 실행기의 분리.

범위 밖: 신청서 자유입력 자동 파기/통계화, GA4·Amplitude 데이터 삭제, 문의 이미지 비공개 전환, 화면 분석 차단, 개인정보처리방침 문구 개정. 이미 별도 논의한 보류 항목을 이번 변경에 섞지 않는다.


## 배포와 관측

- 신규 마이그레이션: `V53__audit_retention_context.sql`. 이전 행의 신규 컬럼은 NULL로 두고 추정 갱신하지 않는다. 운영/Flyway와 스테이지/Hibernate의 기존 스키마 적용 경로를 따른다.
- 공통 실행 환경 변수: `CLEANUP_ENABLED`, `CLEANUP_FIXED_DELAY_MS`(기본 86400000), `CLEANUP_INITIAL_DELAY_MS`(60000).
- 감사 설정: `AUDIT_RETENTION_ENABLED`, `AUDIT_ACCESS_RETENTION_YEARS`(1 또는 2), `AUDIT_TRUSTED_PROXIES`(쉼표 구분 IP/CIDR). 잘못된 보관 연수는 시작 시 오류로 중단한다.
- 기존 `upload.cleanup.enabled`, `feedback.retention.enabled`는 유지한다. 예전 도메인별 fixed-delay/initial-delay 설정은 공통 `cleanup.*`로 옮긴다.
- 지표의 `task` 태그는 `feedback`, `storage`, `audit`만 사용한다. Prometheus의 수집 대상 `job` 라벨과 충돌시키지 않는다.

| Micrometer 지표 | 의미 |
|---|---|
| `cleanup.enabled` | 개별 작업 활성화 1/0 |
| `cleanup.last.run.seconds` | 마지막 시작 시각 (Unix 초) |
| `cleanup.last.success.seconds` | 마지막 실패 없는 완료 시각 (아직 성공 없으면 0) |
| `cleanup.runs` | `outcome=success/failed/skipped`별 실행 횟수 |
| `cleanup.deleted`, `cleanup.failures` | 삭제·실패 건수 누적 |
| `cleanup.held` | 역할 미상 과거 WITHDRAW 보류 수 |
| `cleanup.duration` | 실행 소요 시간 |

저장소 미설정은 skipped로 기록하며 성공 시각을 갱신하지 않는다. 전체 서버 중단은 앱 지표로 감지할 수 없으므로 기존 서버 생존 감시와 함께 사용한다. 예를 들어 활성 작업에 `time() - cleanup_last_success_seconds > 172800` 조건을 두고 시작 직후 유예를 적용한다. 별도 알림 발송 코드는 추가하지 않는다.


## 구현 검증 (2026-10-31)

- 전체 백엔드 `check`: 1,232개 테스트, 실패/오류 0, 제외 1. 포맷 검사 포함.
- 기존 Gradle 파일 감시가 수정 전 산출물을 재사용하여, 파일 감시·빌드 캐시를 끄고 clean 빌드 후 전체 검사를 수행했다. 로컬 테스트 힙은 1,536MB로 실행했다.
- 임시 MySQL 8의 빈 DB에 V53까지 적용하고 Hibernate `validate`, 서버 health, 문의·감사 정리 작업의 0건 정상 실행을 확인했다. 임시 서버·DB는 검증 뒤 종료했다.
- 마이그레이션 번호 중복 검사, 개발 범위/스펙 상태 검사, 문서 링크 검사 통과.
- 위 검증은 로컬·임시 DB에서 수행했다. 실제 환경 적용 전 2년 의무 해당 여부와 신뢰 프록시 설정을 확인한다.
