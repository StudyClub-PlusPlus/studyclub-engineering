# POL-0001 · 역할과 권한

> 시행일: 2026-09-22 · 적용: 콘솔 전 화면 · 사용자 사이트 마이페이지
> 백엔드 대응: [`docs/erd/ACCOUNT.md`](../../../docs/erd/ACCOUNT.md) · [`docs/erd/STUDY_PARTICIPANT.md`](../../../docs/erd/STUDY_PARTICIPANT.md) · [`specs/back-office-login/spec.md`](../../../specs/back-office-login/spec.md)

## 두 층으로 나눈다

권한은 **계정에 붙는 것**과 **스터디마다 서는 것**이 다르다. 한 층으로 합치면 「네비게이터」가
계정 권한처럼 보여 모든 스터디에 미치는 것으로 읽힌다.

| 층 | 값 | 누가 바꾸나 | DB |
|---|---|---|---|
| 계정 권한 | **캡틴** · **크루** | 캡틴이 유저 목록에서 | `ACCOUNT.SYSTEM_ROLE` = `ADMIN` / `MEMBER` |
| 스터디 역할 | **네비게이터** (그 외는 일반 크루) | 캡틴이 스터디 크루 명단에서 | `STUDY_PARTICIPANT.PARTICIPANT_ROLE` = `LEADER` |

- **부반장을 두지 않는다.** 스터디 안의 역할은 네비게이터 하나다 (현장에서 부르는 이름은 「반장」).
- 한 사람이 여러 스터디의 네비게이터일 수 있다. 맡은 스터디마다 행이 따로 선다.
- **담당 캡틴** — 스터디를 생성한 캡틴이 그 스터디의 담당 캡틴이다. 판정은 `STUDY.CREATED_BY = 나` 하나로 한다 (2026-10-07 확정).
  - **담당 캡틴도 그 스터디에 참여한다.** 신청서는 내지 않는다. 스터디를 만들 때는 반이 없어서 명부(`STUDY_PARTICIPANT`)에 넣지 않는다. 모집이 끝나고 **반 편성 때 캡틴이 담당 캡틴의 반도 지정하면** 그때 명부에 들어간다. 그 뒤로 출석·출석률·완주는 크루와 같다.
  - 모집 정원에는 포함하지 않는다 — 신청 행이 없기 때문이다.
  - 명부의 역할 값은 크루와 같은 `MEMBER` 다. 캡틴용 값을 따로 두지 않는다. 화면의 「캡틴」 표시는 `CREATED_BY` 로 붙인다.
  - `CREATED_BY` 가 NULL 인 스터디(컬럼이 생기기 전에 등록된 것)는 담당 캡틴이 없다. 담당 캡틴만 하는 일은 그 스터디에서 **캡틴 누구나** 한다.
- 네비게이터는 캡틴이 그 스터디 참여자(신청 후 배정된 크루) 중에서 고른다. 그래서 네비게이터는 모집 정원에 포함된다.
- 「캡틴」을 `LEADER`·리더로 쓰지 않는다. 캡틴은 계정 권한(`ADMIN`), 네비게이터는 스터디 역할(`LEADER`)이다.

## 권한표

### 스터디 단위 — 네비게이터 권한은 담당 스터디에 국한

| 하는 일 | 캡틴 | 네비게이터 | 크루 |
|---|---|---|---|
| 스터디 크루 명단 열람 | ✓ | ✓ | — |
| 스터디 정보 수정 | ✓ | ✓ | — |
| 출석 현황 수정 | ✓ | ✓ | — |
| 회차 관리 (추가·수정·삭제) — 담당 반에 한해 | ✓ | ✓ | — |
| 스터디 공지 발행 | ✓ | ✓ | — |

> 「회차 관리 — 담당 반에 한해」 가 캡틴에게도 걸리는지는 미확정이다. 지금 서버는 캡틴에게 모든 분반을 허용한다 ([회차 스펙](../../../specs/study-meeting/spec.md#미확정)).

### 신청 폼 · 신청 결과 (2026-10-04 확정)

| 하는 일 | 담당 캡틴 | 다른 캡틴 | 네비게이터 | 크루 |
|---|---|---|---|---|
| 신청 폼 수정 | ✓ | — (읽기만) | — | — |
| 신청 폼 열람 (백오피스) | ✓ | ✓ | — | — |
| 신청 결과 열람 | ✓ | ✓ | — | — |
| 스터디 신청서 제출 | — (반 편성 때 명부에 들어간다) | ✓ | — (이미 명부에 있음) | ✓ |

> 내 스터디 카드의 **스터디 관리** 버튼 — 담당 캡틴은 **백오피스 스터디 상세**로, 네비게이터는 사용자 사이트 스터디 관리(일정·출석부)로 간다.
> 담당 캡틴은 반 편성 전(명부에 없을 때)에도 내 스터디에 카드가 생긴다 — `GET /api/me/studies` 가 `CREATED_BY = 나` 인 스터디를 함께 준다 ([내 스터디 스펙](../../../specs/my-studies/spec.md)).

## 판정 규칙

- **스터디 공개는 정보 수정과 다른 권한이다.** 묶으면 담당 스터디를 굴리는 네비게이터가 사이트에
  스터디를 세울 수 있게 된다 — 세우는 일은 캡틴의 판단이다.
- **반 편성은 스터디에 하는 일이지만 캡틴만 갖는다.** 누가 어느 반에 들어가는지는 한 사람이 정한다.
- **출석 체크는 권한이 아니다.** 보이스룸에서 `/StudyStart` 로 그날 출석을 여는 일은 누구나 한다.
  권한이 필요한 것은 **이미 기록된 출석을 고치는 일**이다.
- 역할을 줄 수 있는 것은 캡틴뿐이다 — 줄 수 있는 사람이 여럿이면 권한이 조용히 번진다.
- 백오피스는 캡틴만 들어간다. **네비게이터는 백오피스에 들어오지 못한다** (2026-10-04 확정). 최초 캡틴은 SQL 로 세운다 ([back-office-login](../../../specs/back-office-login/spec.md)).

## 백엔드와 어긋난 것

| 무엇 | 지금 백엔드 | 기획 |
|---|---|---|
| `PARTICIPANT_ROLE` 에 `CO_LEADER`(부반장) | 있음 | **없앤다** — 스터디 역할은 네비게이터 하나 |
| 문서의 역할 표기 | `ADMIN`·「캡틴」을 섞어 씀 | 문서·화면은 **캡틴·크루·네비게이터**. DB 값은 위 매핑표대로 |
| 신청 폼 저장 권한 | 캡틴이면 누구나 · 사용자 사이트 경로는 네비게이터도 허용 | 담당 캡틴(`CREATED_BY = 나`)만. 사용자 사이트 경로(`PUT /api/studies/{studyId}/application-form`)는 코드에서 지운다 |
| 내 스터디의 담당 캡틴 표시 | 명부 행만 준다. 담당 캡틴 여부를 알려 주지 않음 | `CREATED_BY = 나` 인 스터디도 주고 `captain` 플래그를 단다 |
| 담당 캡틴의 반 지정 | 없음. 반 지정 API 는 명부 행이 있는 크루만 받는다 | 반 편성 화면에서 담당 캡틴의 반도 지정한다. 지정하면 명부 행이 생긴다 ([분반 스펙](../../../specs/study-group/spec.md#담당-캡틴의-반-지정)) |

> 스터디를 만들 때 담당 캡틴을 명부에 넣는 안(역할 값 `CAPTAIN` 추가 · 생성 시 기본 분반 생성 · 백필 마이그레이션)은 **채택하지 않았다** (2026-10-07).
> 만드는 시점에는 반이 없다. 반은 모집이 끝난 뒤 편성하므로, 담당 캡틴도 그때 크루와 함께 반을 받는다. 담당 판정은 이미 있는 `STUDY.CREATED_BY`(V29)로 하므로 역할 값도 필요 없다.
