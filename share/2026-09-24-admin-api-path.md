# 백오피스가 쓰는 창구와 사용자가 쓰는 창구를 따로 만든다

## 미리 알아야 할 것

처음 보는 단어부터 풉니다. 이거 네 개만 알면 아래는 다 읽힙니다.

| 단어 | 뜻 |
|---|---|
| **API** | 화면(웹페이지)이 서버에게 "이 정보 주세요", "이거 저장해 주세요" 하고 말을 거는 **창구** |
| **엔드포인트** | 그 창구의 **주소**. `/api/studies` 처럼 생겼다. 창구마다 주소가 다르다 |
| **사용자 사이트** | 크루(참가자)가 쓰는 화면. studyclub-plusplus.com |
| **백오피스** | 운영하는 사람만 들어가는 **관리자 화면**. 크루는 주소를 알아도 못 들어간다 |

사람 종류도 두 가지가 나옵니다. 우리 팀 규칙(POL-0001)에서 정한 이름입니다.

- **캡틴** — 사이트 전체를 관리하는 사람. 모든 스터디를 볼 수 있다
- **네비게이터** — **자기가 맡은 스터디 하나**만 운영하는 사람

그리고 중요한 전제 하나: **백오피스에는 캡틴만 들어갑니다.** 네비게이터는 못 들어갑니다.

## 한 줄 요약

**백오피스가 쓰는 창구는 주소를 `/api/admin/...` 으로 따로 판다.**
그리고 같은 일을 사용자 사이트에서도 한다면, **창구를 하나 더 만든다.** 돌려쓰지 않는다.

## 비유 — 은행 창구

은행에 갔다고 생각해 봅시다.

- **일반 창구** — 아무나 줄 서서 입출금을 한다
- **직원 전용 문** — 사원증을 찍어야 열린다. 그 안에서는 금고도 만지고 남의 계좌도 조회한다

두 곳을 **한 창구로 합치면** 어떻게 될까요? 직원용 기능을 일반 손님이 실수로 누르지 않게
막는 일을, 창구 직원이 **매번 기억해서** 해야 합니다. 한 번만 깜빡하면 사고입니다.

문을 아예 따로 내면 **"이 문은 사원증"** 한 문장이 모든 걸 막아줍니다.
우리가 고른 게 이겁니다. `/api/admin` 이 그 사원증 문입니다.

## 왜 — 지금 뭐가 문제였나

두 가지가 있었습니다.

**하나.** 백오피스용 창구와 사용자용 창구가 **한 파일에 섞여** 있었습니다.
그래서 "이건 관리자만" 을 **창구마다 하나씩 손으로 붙여야** 했습니다. 하나 빠뜨리면 그대로 구멍입니다.

**둘.** 정리하다가 구멍이 하나 나왔습니다.
**스터디 신청서 양식을 고치는 기능이 백오피스에만 있었습니다.**
그런데 백오피스는 캡틴만 들어갑니다. 즉 —

> 네비게이터는 **자기가 맡은 스터디의 신청서 양식을 영영 못 고친다.**

기능이 없어서가 아니라, **문이 하나뿐이라서** 막힌 겁니다.

## 정해진 것

1. **백오피스가 부르는 창구는 `/api/admin` 아래 둔다.** 뒤에 붙는 주소는 그대로 이어 쓴다
   → `/api/admin/studies/{스터디번호}/applications`
2. **파일도 관객으로 나눈다.** 사용자용 창구와 관리자용 창구를 한 파일에 같이 두지 않는다
3. **`/api/admin` 은 기본이 "로그인 필수"** 다. 여기에 예외로 공개 창구를 뚫지 않는다
4. **파일 이름은 `Admin...`** 으로 시작한다 (`BackOffice...` 는 안 쓴다 — 화면 이름이라서)
5. **쓰는 사람이 둘이면 창구도 둘이다.** 안쪽에서 처리하는 내용은 같이 쓰되,
   **"누가 들어올 수 있나" 검사만 각자 붙인다**

5번을 신청서 양식으로 보면 이렇습니다.

| 창구 주소 | 누가 쓰나 | 들여보내는 기준 |
|---|---|---|
| `PUT /api/studies/{번호}/application-form` | 그 스터디 **네비게이터** 또는 캡틴 | 스터디 하나 범위 |
| `PUT /api/admin/studies/{번호}/application-form` | **캡틴만** (백오피스) | 사이트 전체 범위 |

> 왜 창구 안에서 `if (백오피스에서 왔나)` 로 갈라치면 안 되나요?
> 그 `if` 한 줄이 **권한을 우회하는 지점**이 되기 때문입니다. 조건을 잘못 쓰거나
> 나중에 누가 지워도 아무도 모릅니다. 문을 따로 내면 지울 수가 없습니다.

## 팀 의견 — 왜 "편한 쪽" 을 안 골랐나

처음에는 창구 하나를 같이 쓰는 게 편해 보였습니다. 팀 논의에서 반대 의견이 나왔고 그게 맞았습니다.

> 유저와 백오피스는 **필요한 정보와 할 수 있는 일이 다르다.** 결국 나누게 될 가능성이 높다.
> 유저에게 필요 없는 기능·데이터까지 일반 창구에 노출되는 구조는 어색하고,
> 캡틴 기능은 캡틴만 접근하게 나누는 게 좋다.

나눠서 얻는 것 — 하나씩 풀면 이렇습니다.

| | 무슨 뜻인가 |
|---|---|
| **권한 관리** | "이 문은 사원증"처럼 **주소 단위**로 규칙을 건다. 창구마다 붙이는 것보다 빠뜨리기 어렵다 |
| **최소 권한** | 유저에게 필요 없는 기능이 **애초에 그 창구에 없다.** 막을 필요도 없어진다 |
| **개인정보** | 관리 화면은 앞으로 이메일·활동 기록을 더 다룬다. 섞여 있으면 나중에 떼는 비용이 커진다 |
| **실수 방지** | 응답 모양을 같이 쓰다가 **관리자만 봐야 할 항목이 일반 창구에 딸려 나가는** 사고를 줄인다 |
| **변경 영향** | 백오피스 요구로 창구를 고쳐도 사용자 화면이 흔들리지 않는다 |
| **응답 최적화** | 유저에겐 필요한 것만, 백오피스엔 관리용 상세를 준다 |
| **감사 로그** | "누가 관리 작업을 했나"를 따로 기록·추적하기 쉽다 |
| **역할 확장** | 나중에 역할이 더 늘어도 구조가 버틴다 |

**다만 모든 걸 다 쪼개자는 말은 아닙니다.** 일반 유저용과 관리자용, **그 경계선 하나만** 긋습니다.
그 안에서는 지금처럼 갑니다.

## 영향 — 누가 무엇을 해야 하나

| 누가 | 무엇을 |
|---|---|
| **백오피스 프론트** | 부르는 주소 앞에 `/api/admin` 이 붙습니다. 옛 주소 `/back-office/...` 는 없어집니다 |
| **사용자 사이트 프론트** | 네비게이터가 신청서 양식을 고치는 화면을 붙일 수 있습니다 (`PUT /api/studies/{번호}/application-form`) |
| **백엔드** | 새 창구를 만들 때 **"이건 누가 쓰나"부터** 정하고 주소를 고릅니다. 규칙 전문: [`docs/backend-development-guide/api/endpoint-convention.md`](../docs/backend-development-guide/api/endpoint-convention.md) |

## 아직 안 정해진 것 (기획 확인 필요)

- 네비게이터가 **신청자 목록**도 사용자 사이트에서 봐야 하나? 지금은 백오피스(캡틴)에만 있습니다
- 로그인 정보 자체에 권한을 새겨 넣는 방식(`hasRole`)으로 올리는 건 **다음 작업**으로 미뤘습니다.
  지금은 주소를 나누고 검사 함수를 부르는 방식으로 막습니다
- POL-0001 이 없애기로 한 역할(`CO_LEADER`)이 코드에 아직 남아 있습니다 — 제거는 별도 작업
