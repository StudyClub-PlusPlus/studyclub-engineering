# 서버 이상을 디스코드로 알린다 — 봇이 올리고, 본문은 우리가 쓴다

## 미리 알아야 할 것

- **Grafana** — 서버 상태를 그래프로 보는 화면이다. 이미 쓰고 있다
  (주소는 Notion 「알림 시스템 — 구조와 사용법」 참조. 구글 계정으로 로그인합니다).
- **메트릭** — "지금 어떤 상태인가" 를 나타내는 숫자다. 요청이 초당 몇 건인지, 응답이 몇 초
  걸리는지 같은 것. 로그가 "무슨 일이 있었나" 라면 메트릭은 "지금 어떤 상태인가" 다.
- **알림(alert)** — 그 숫자가 정해둔 선을 넘으면 사람에게 알리는 기능이다.
  **지금은 없다.** 누군가 화면을 봐야만 이상을 안다.
- **webhook** — "여기로 메시지를 보내줘" 라고 알려주는 주소 하나. 디스코드는 채널마다 이걸
  만들 수 있다.
- **봇(bot)** — 서버에 초대해 둔 프로그램 참가자다. 우리는 `캡틴` 봇을 이미 쓰고 있다.

## 한 줄 요약

서버에 이상이 생기면 디스코드 알림 채널에 자동으로 글이 올라가게 만들었고,
**Grafana 기본 형식 대신 본문을 직접 쓰려고, 채널 webhook 이 아니라 우리 봇으로 올린다.**

## 왜 — 지금 뭐가 문제인가

대시보드는 다 만들었는데 **알림이 없다.** 5xx 에러가 치솟아도 그 시각에 화면을 보고 있던
사람만 안다. 새벽이면 아침까지 아무도 모른다.

알림을 보내는 방법은 두 가지였다.

**1. 채널 webhook** — 디스코드에서 채널마다 주소를 하나 만들고, 그 주소로 글을 던진다.
Grafana 에 이걸 쓰는 버튼이 있어서 설정이 제일 쉽다.

**2. 봇 토큰** — 이미 서버에 있는 우리 봇의 자격증명으로 디스코드에 글을 올린다.

1번은 **메시지 모양을 우리가 못 정한다.** Grafana 가 정해 둔 형식대로 라벨과 설명이 전부
나열돼 본문이 625자가 되고, 숫자의 단위도 색도 손댈 수 없다. 알림은 새벽에 졸린 눈으로 읽는
글이라 이게 그대로 비용이 된다.

2번은 본문을 우리가 쓴다. 지금 형식은 200자 안쪽이고 무슨 일인지 · 뭘 볼지 · 바로 가는 링크 ·
숫자, 네 가지만 남겼다. 실제로 둘을 나란히 받아 본 캡처는 Notion 문서에 있다.

덤으로 관리할 것도 늘지 않는다. 봇은 이미 서버에 들어와 있고 권한이 역할로 묶여 있어서
채널이 늘어도 새로 만들 게 없다.

## 정해진 것

**알림은 봇이 올린다.** 알림 채널은 지금 쓰는 `03-system-alerts` 를 그대로 쓴다.

무엇을 알릴지는 네 가지다.

| 알림 | 언제 | 급함 |
|---|---|---|
| ERROR 로그 발생 | 에러 로그가 **한 건이라도** 찍히면 바로 (알림에서 로그로 바로 가는 링크 포함) | 높음 |
| 로그 수집 중단 | 앱은 로그를 내는데 저장소에 안 들어옴 | 높음 |
| api 다운 | 서버에서 숫자를 걷어오지 못하는 상태가 2분 지속 | 높음 |
| 5xx 급증 | **API 주소별로** 서버 에러 비율이 5% 초과 | 높음 |
| 5xx 발생(건수) | **API 주소별로** 서버 에러가 3건 초과 | 높음 |
| DB 연결 이상 | 데이터베이스 연결을 못 얻는 상태가 2분 지속 | 높음 |
| 디스크 부족 | 앱이 쓰는 디스크 여유가 15% 미만 | 높음 |
| 응답 지연 | **API 주소별로** 느린 쪽 5% 가 2초 넘게 기다림 | 보통 |
| JVM 힙 고갈 임박 | 메모리 사용률이 10분간 90% 초과 | 보통 |
| GC 과부하 | 앱이 일 대신 메모리 정리에 시간의 절반 이상을 씀 | 보통 |
| 파일 디스크립터 고갈 임박 | 열어둔 파일 수가 한도의 80% 초과 | 보통 |

## 알림이 오면 이렇게 보입니다

```
🔴 stage · 발생 1건 · 해소 2건
✅ 5xx 급증(/), 디스크 부족
┌ 🔴 5xx 급증 · /api/studies
│ 5xx 비율이 5% 를 넘었다
│ 응답 코드별 그래프를 본 뒤 같은 시각 로그를 본다.
│ 📊 대시보드  ·  🔎 쿼리
│ 5xx 비율 (5분) : 100 %
│ studyclub · stage · critical   오늘 오전 2:13
└
```

**무슨 일인지 · 뭘 봐야 하는지 · 바로 가는 링크 · 숫자**, 네 가지를 한눈에 담았습니다.
색으로 급한 정도를 나눕니다 — 🔴 빨강은 바로 봐야 하는 것, 🟠 주황은 지켜볼 것.
시각은 보는 사람의 시간대로 나옵니다.

**끝났다는 알림은 한 줄입니다.** 카드를 다시 그리지 않고 이름만 `✅` 뒤에 붙입니다.
"언제 정상으로 돌아왔는지"는 남으면서 채널이 조용합니다.

**`@everyone` 은 어떤 경우에도 울리지 않게 막아 뒀습니다.** 급한 것만 사람을 부르도록
할 예정인데, 누구를 부를지(팀 역할)는 아직 정해지지 않아 지금은 멘션이 없습니다.

## 영향 — 누가 무엇을 해야 하나

**stage 는 동작합니다.** 알림 규칙 **11개**가 전부 정상 평가 중이고, 테스트 알림이
`03-system-alerts` 채널에 실제로 도착했습니다. 끝에서 끝까지(규칙 → 라우팅 → 봇 →
디스코드) 확인된 상태입니다.

**인프라 / k8s 관리자** — 둘입니다.
1. **볼륨 마운트** (나중에 요청드립니다) — 지금 알림 규칙은 Grafana 안에만 있어서,
   Grafana 를 다시 세우면 사라집니다. 규칙을 어느 정도 다듬은 뒤 YAML 로 내보내서
   `/etc/grafana/provisioning/alerting/` 에 얹어 달라고 요청드릴 예정입니다.
   **아직은 아닙니다** — 얹는 순간 UI 에서 못 고치게 되므로, 임계값을 먼저 굳힙니다
2. **노드(서버) 전체의 디스크 알림** — 앱이 쓰는 디스크는 우리가 보지만, 노드 전체 용량은
   프로젝트 필터를 통과하지 못해 우리 Org 에서 조회가 안 됩니다. 클러스터 차원의 알림으로
   인프라 쪽에 둬 주세요

**BE** — PromQL 은 stage 실제 지표로 확인했습니다(규칙 4개 모두 정상 평가).
임계값(5xx 5%, p95 2초)이 우리 서비스에 맞는지만 봐 주세요. 낮으면 알림이 배경음이 되고,
배경음은 아무도 안 봅니다.

**전원** — 토큰이 채워지면 `03-system-alerts` 채널에 알림이 오기 시작합니다. 첫 줄에
어느 환경(stage/prod)인지, 무슨 알림인지, 관측값이 얼마인지가 함께 옵니다.
