# 회차를 만드는 방식과 출석 체크 방식은 「출석 방식」 값 하나로 정한다

## 미리 알아야 할 것

- **스터디와 클럽.** 스터디는 한 번 모집해서 한 번 진행한다. 클럽은 같은 이름으로 매달·매 기수 반복한다
  (얼리버드 1기·2기·3기처럼). 시스템에는 이 구분이 `STUDY_KIND` 라는 값으로 이미 있다
- **기수.** 클럽의 한 번 진행분. 스터디도 기수가 딱 하나 있다고 본다. 시스템 이름은 `STUDY`
- **분반.** 한 기수 안에서 시간대별로 나눈 반 (예: 수요일반, 미주반). 시스템 이름은 `STUDY_GROUP`
- **회차.** 반의 N번째 모임. 출석은 회차 단위로 찍는다. 시스템 이름은 `STUDY_MEETING`
- **캡틴·네비게이터.** 캡틴은 운영진. 네비게이터는 맡은 반을 진행하는 사람(현장 이름 「반장」)
- **보이스룸 출석.** 지금 스터디는 네비게이터가 디스코드 음성 채널에서 `/StudyStart` 명령으로 그날 출석을 연다
- **ERD.** 데이터를 어떤 표·칸에 저장할지 적은 설계도. `docs/erd/` 에 있다

## 한 줄 요약

**스터디냐 클럽이냐로 출석 방식을 가르지 않는다.** 기수마다 「출석 방식」(`ATTENDANCE_MODE`)을 따로 두고,
캡틴이 스터디를 등록할 때 고른다. 방식이 달라도 **결과는 같은 표(회차 × 회원)에 저장**해서
출석률·완주·내 스터디 출석 칸은 한 가지 계산으로 돈다.

## 왜 — 지금 뭐가 문제인가

스터디와 클럽은 출석을 전혀 다르게 한다. 그런데 **클럽끼리도 서로 다르다.**

| 어디 | 회차 | 출석 체크 |
|---|---|---|
| 스터디 (예: DDIA 2판) | 캡틴이 일정을 먼저 잡고, 시작 뒤에는 네비게이터가 회차를 운영 | 네비게이터가 디스코드 보이스룸에서 체크 |
| 클럽 얼리버드 | 매일 | 기상 목표 ±15분 안에 시각이 찍힌 사진 → 30분 이상 활동 → 다시 사진. 디스코드 텍스트 출석부를 복사해 각자 채우고 사진 두 장 첨부 |
| 클럽 WEEKLY X | 매일 (주간 목표) | 엑셀에 주간 목표 공부 시간을 적고, 매일 공부 시간을 기입 |
| 클럽 Daily LeetCode | 매일 | LeetCode 아이디로 연속 풀이 기록(스트릭)을 확인해 자동 체크 |

그래서 `STUDY_KIND`(스터디/클럽)로 나누면 클럽 세 곳을 한 방식으로 묶게 된다. 맞지 않는다.
`STUDY_KIND` 는 **모집을 한 번 하느냐 반복하느냐**를 말하는 값이지 출석을 말하는 값이 아니다.

> 비유: 학교의 「정규반/방과후반」 구분과 「출석부를 선생님이 부르느냐, 학생이 카드를 찍느냐」는
> 서로 다른 질문이다. 방과후반이라도 반마다 출석 방식은 다를 수 있다.

## 제안 — 출석 방식 네 가지

| 값 | 예 | 회차는 어떻게 생기나 | 출석은 어떻게 찍나 |
|---|---|---|---|
| `MEETING` 모임형 | 스터디 | 캡틴이 반 일정(요일·시각·기간)을 정하면 한꺼번에 생긴다. 시작 뒤에는 네비게이터가 하나씩 더하거나 고친다 | 네비게이터가 보이스룸 `/StudyStart`. 사후 수정 가능 |
| `DAILY_PROOF` 인증형 | 얼리버드 | 기간 안의 매일 자동 | 회원이 시작·종료 인증을 올리고 네비게이터가 확인 |
| `DAILY_LOG` 기록형 | WEEKLY X | 매일 자동 + 주간 목표 | 회원이 공부 시간을 적는다. 목표와 비교해 판정 |
| `EXTERNAL` 외부 연동 | Daily LeetCode | 매일 자동 | 외부 기록(스트릭)을 읽어 자동 판정 |

세부 원칙:

- **값은 기수(`STUDY`)에 둔다.** 프로그램(`STUDY_PROGRAM`)에 두면 클럽이 다음 기수에서 방식을 바꿀 수 없다
- **기본값.** 스터디는 `MEETING`. 클럽은 등록할 때 반드시 고른다
- **저장은 하나로.** 어느 방식이든 결과는 `STUDY_MEETING`(회차) × `STUDY_ATTENDANCE`(출석)에 쌓는다.
  매일 도는 클럽은 **하루가 한 회차**다
- **「회차 추가」 버튼은 `MEETING` 에서만.** 다른 방식은 회차가 매일 자동으로 생기므로 손으로 더하면 날짜 순서가 깨진다
  (playground 내 스터디 화면의 회차 추가 프로토타입이 이 전제다)

### 단계 — 한꺼번에 만들지 않는다

1. **1단계:** `MEETING` 만 제대로 만든다. 클럽은 「수동」으로 받는다 — 네비게이터가 결과만 넣거나 시트에서 한 번에 가져온다.
   클럽마다 방식이 다르고 자주 바뀌어서, 입력 화면부터 만들면 비용이 효과보다 크다
2. **2단계:** 사람 손이 안 드는 `EXTERNAL`(LeetCode)을 자동화한다
3. **3단계:** 사진 인증(`DAILY_PROOF`)·시간 기록(`DAILY_LOG`). 파일 업로드와 숫자 칸이 필요해 데이터 모델이 커진다

## 지금 쓰는 구글 시트는 어디로 가나

스터디 운영 시트에는 「분반 정보」와 「반별 출석 현황」 두 장이 있다. 칸별로 ERD 와 맞춰 보면:

| 시트 칸 | 시스템에서 | 상태 |
|---|---|---|
| 반 제목 · 반별 참석자 이름 · 네비게이터 이름 | `STUDY_GROUP.NAME` · `STUDY_PARTICIPANT`(역할 `LEADER` = 네비게이터) | 있음 |
| 스케줄: 주차 · 날짜 · 제목 | `STUDY_MEETING` — 날짜 = `SCHEDULED_AT`, 주차 = `MEETING_NO`, 제목 = `TITLE` | 주차·제목은 ERD 에 **미확정**으로 남아 있다 |
| 출석부: 참석 여부 | `STUDY_ATTENDANCE.STATUS` | 있음 |
| 출석부: 반 이동 여부 | `STUDY_ATTENDANCE.STUDY_CLASS_ID` (실제로 참석한 반을 적는다) | 있음 |
| 스케줄: 발표자1 · 발표자2 / 출석부: 발표 여부 · 발표 예정 여부 · 발표 펑크 여부 | **없음** | **새 개념.** 예: 회차별 발표자 표 + 상태(예정 · 완료 · 펑크) |

## 물어볼 것

1. **1단계 범위** — `MEETING` + 클럽 「수동」으로 시작해도 되나?
2. **발표** — 발표 기록을 시스템에 넣을까? 넣는다면 **완주 판정에 들어가나?** (예: 발표 펑크를 결석처럼 셀까)
3. **기록형(WEEKLY X)의 판정 단위** — 하루하루 출석으로 보나, 주간 목표 달성 여부로 보나?
4. **인증형(얼리버드)의 확인 주체** — 사진을 네비게이터가 하나씩 확인하나, 올리면 바로 출석인가?
5. **주차 = 회차인가** — 시트의 「주차」와 시스템의 「회차 번호」를 같은 것으로 봐도 되나? (주 2회 모이는 반이면 달라진다)

## 영향 — 누가 무엇을 해야 하나

- **기획·캡틴:** 위 「물어볼 것」 다섯 개에 답한다. 특히 1번이 정해져야 개발이 시작된다
- **백엔드:** 1번이 정해지면 `STUDY` 에 `ATTENDANCE_MODE` 칸을 더하고 ERD(`docs/erd/STUDY.md`)를 고친다.
  2번이 「넣는다」면 발표자 표를 ERD 에 새로 그린다
- **프론트·playground:** 「회차 추가」 버튼을 `MEETING` 기수에만 보이게 한다. 클럽 카드에는 두지 않는다
- **정책 문서:** 역할 권한표(`01-planning/_registry/policies/POL-0001-roles.md`)에 「회차 등록」 행이 없다 — 이번에 함께 정한다
