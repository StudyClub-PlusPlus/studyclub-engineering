# 반복으로 만든 회차의 「묶음 ID」를 저장하기로 — 지금 쓰는 기능은 없고, 나중을 위해 남긴다

## 미리 알아야 할 것

| 단어 | 뜻 |
|---|---|
| **회차** | 스터디의 한 번 모임. DB 표 이름은 `STUDY_MEETING` |
| **반복 추가** | 네비게이터가 「매주 수요일, 4주」처럼 골라 회차 여러 개를 한 번에 만드는 기능 |
| **묶음 ID (`SERIES_ID`)** | 한 번에 같이 만든 회차들에 똑같이 붙여 두는 이름표. "이 회차들은 같은 반복에서 나왔다"는 표시 |
| **UUID** | 겹치지 않게 무작위로 만든 긴 문자열 (`3f2b…`). 이름표 값으로 쓴다 |

배경: [2026-10-02 결정](2026-10-02-study-meeting-decisions.md)에서는 「반복은 만들 때만 쓰고, 묶음은 저장하지 않는다」로 정했다. 이번에 그중 **저장 여부만** 바꿨다.

## 한 줄 요약

반복으로 회차를 2개 이상 만들면, 서버가 그 회차들에 **같은 묶음 ID 를 붙여 저장한다.** 화면은 아직 이 값을 쓰지 않는다. 삭제·수정은 지금처럼 한 회차씩이다.

## 비유 — 스티커 뒷면에 같은 번호 적어 두기

10-02 결정 때의 비유는 "달력에 스티커 네 장을 한 번에 붙이고, 붙인 뒤에는 그냥 네 장"이었다.
이번 결정은 **스티커 뒷면에 같은 번호를 적어 두는 것**이다. 지금은 아무도 뒷면을 보지 않는다.
하지만 나중에 「이 묶음 전체 떼기」 버튼을 만들 때, 번호가 적혀 있어야 어느 스티커끼리 한 묶음인지 안다.
번호 없이 붙여 버린 스티커는 나중에 다시 묶을 방법이 없다.

## 왜 — 지금 저장해야 하는 이유

- 반복 단위로 고치거나 지우는 기능(「이후 반복 모두 삭제」 같은 것)이 **나중에 생길 수 있다** (기획 판단)
- 그 기능은 "어떤 회차들이 같이 만들어졌는지"를 알아야 한다. 이 정보는 **만드는 순간에만** 얻을 수 있다
- 지금 저장하지 않으면, 그 사이에 만든 반복 회차는 기능이 생겨도 묶을 수 없다

## 정해진 것

1. **`STUDY_MEETING` 에 `SERIES_ID` 칸을 더한다.** 글자 36자(UUID). 비어 있어도 된다
2. **값은 서버가 만든다.** 한 번의 추가 요청으로 회차가 2개 이상 생기면 UUID 하나를 만들어 모두에 넣는다. 1개만 만들면 비워 둔다. 화면이 보내는 요청 모양은 그대로다
3. **회차를 수정해도 묶음 ID 는 바뀌지 않는다.** 시각을 옮겨도 같은 묶음이다
4. **삭제는 지금처럼 한 회차씩이다.** 지운 회차의 같은 묶음 다른 회차는 그대로 남는다
5. **화면에는 아직 아무것도 바뀌지 않는다.** 「이후 반복 모두」 버튼과 목록의 반복 표시는 두지 않는다. 서버 응답에도 아직 내보내지 않는다
6. **이미 만든 회차는 비워 둔다.** 예전에 반복으로 만든 회차도 묶을 근거가 없어 채우지 않는다

## 영향 — 누가 무엇을 해야 하나

- **백엔드**:
  - 마이그레이션 `V{n}__add_study_meeting_series_id.sql` 로 칸을 더한다. `n` 은 머지할 때 beta 최신 번호의 다음이다 — 지금 beta 는 `V25` 이고, 열린 PR 여럿이 이미 `V26` 을 쓰고 있어 번호를 미리 정하지 않는다
  - 회차 추가 API 가 2개 이상일 때 UUID 를 넣게 고친다. 테스트: 1개 → null, 여러 개 → 모두 같은 값, 수정 후에도 그대로
- **프론트**: 할 일 없음. playground 는 이미 브라우저 저장소에 같은 값(`seriesId`)을 남긴다
- **기획**: 반복 단위 수정·삭제가 필요해지면 그때 화면 기획을 새로 연다. 그 전까지 이 값은 "적어만 두는" 상태다
